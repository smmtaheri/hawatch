# گزارش پیاده‌سازی و QA طراحی جدید هواچ

## موتور مشترک هشدار — ۲ اکتبر ۲۰۲۶

سیاست `walking-v1` جایگزین نگاشت قدیمی شدت به نام پدیده شده است.
قواعد، نمایش مقصد/مسیر و migration در [weather-warnings.md](weather-warnings.md)
مستندند. باد بسیار شدید می‌تواند قرمز شود؛ ابر و بارش معمولی هشدار خودکار
ندارند. خلاصهٔ روز، هوای غالب و خطرهای زمان‌دار را جدا نمایش می‌دهد.

## هشدار زرد باد — نسخهٔ پیشین در ۲ اکتبر ۲۰۲۶

باد و تندباد از سطح `change` (زرد) استفاده می‌کنند؛ هشدار باد به‌تنهایی
کارت ساعتی یا مسیر را critical نمی‌کند و مثلث قرمز ندارد. رکوردهای قبلی
با آسمان بدون هشدار قرمز و شدت critical ناشی از باد، هنگام خواندن به زرد
تبدیل می‌شوند و نیازی به migration یا ingest دستی نیست. شدت قرمز مستقلِ
رعدوبرق و بارش حفظ می‌شود. در کارت ساعتی، جزئیات تخصصی و مقدار باد/تندباد
فقط در صورت عبور از آستانهٔ مربوط زرد هستند؛ عنوان وضعیت آسمان و باد
عادی رنگ نمی‌گیرند. برچسب روز در خلاصه همیشه رنگ عادی تم دارد و فقط متن
بعد آن بسته به شدت normal/change/critical رنگ عادی، زرد یا قرمز می‌گیرد.

## یکپارچگی بصری — ۲ اکتبر ۲۰۲۶

رنگ سطح، حاشیه، حالت انتخاب‌شده، گوشهٔ کارت‌ها و کنترل‌ها و scale نقش‌های
متنی مشترک در `shared.css` یکپارچه شدند. override سطح ۴۲٪ موبایل روشن مسیر
حذف شد؛ سطح عادی همهٔ صفحات در روشن ۷۲٪ و در تاریک ۷۰٪ است. ساعت، دما،
وضعیت، باد و آیکون هوا بین مقصد و مسیر scale یکسان دارند؛ ساعت رسیدن مسیر
هم‌رنگ ساعت مقصد و ضخیم است. عنوان و توضیح صفحه، عنوان بخش و عنوان کارت
نیز قرارداد responsive مشترک دارند.

Chromium با پاسخ‌های کنترل‌شدهٔ API محلی، چهار صفحهٔ مقصد، مسیر، خانه و
اشتراک را در عرض‌های ۳۲۰، ۳۹۰، ۷۶۸، ۱۰۲۴ و ۱۴۴۰px و هر دو تم بررسی کرد
(۴۰ حالت). برابری رنگ سطح، حاشیه، radius، عنوان‌ها، نقش‌های دادهٔ هوا و
حالت انتخاب‌شده، نبود overflow صفحه/کارت و خطای runtime تأیید شد. ۱۶
تصویر از موبایل و دسکتاپ برای بازبینی تهیه شد. این بررسی، داده و مرورگر
کنترل‌شده است و ادعای آزمون دستگاه واقعی یا سرور production نیست.
تصاویر اصلی و رفتار API، SEO، اشتراک‌گذاری و خرید تغییر نکردند.

## رفتار نهایی

- خانه، مقصدها، صفحهٔ مستقل مسیرها، مقصد، مسیر، ورود و حساب و اشتراک با CSS، فونت Vazirmatn، پس‌زمینه‌ها و SVGهای بستهٔ نهایی اجرا شده‌اند. ۶۰ تصویر مرجع در `design/screens/new-design/` همراه manifest و hash نسخه‌بندی شده‌اند. فونت Estedad و OFL قبلی، تصاویر اصلی و مستندات Login قبلی حفظ شده‌اند.
- فهرست‌ها و جست‌وجوی گروه‌بندی‌شده از API واقعی استفاده می‌کنند. جست‌وجوی مقصد و مسیر مستقل است؛ debounce، لغو درخواست جست‌وجو و کنترل پاسخ قدیمی دارند. لینک‌ها canonical و قابل بازکردن در تب جدید هستند.
- آدمک، ورود شماره/کد و وضعیت حساب را در منوی کوچک همان هدر باز می‌کند؛ بدون backdrop، قفل اسکرول یا تغییر URL. احراز هویت session واقعی موجود حفظ شده است؛ فرانت شماره یا کد ثابت ندارد. روزهای باقی‌مانده فقط برای عضویت مدت‌دار از تاریخ پایان واقعی محاسبه می‌شوند. قیمت یا پرداخت تازه‌ای اضافه نشده است.
- تمام دماهای UI حسی هستند؛ کمینه/بیشینه از همهٔ رکوردهای روز انتخاب‌شده محاسبه می‌شود. نبود داده با عدد ساختگی یا دمای مطلق پر نمی‌شود. جزئیات تخصصی پیش‌فرض بسته است، هر بار فقط یک ساعت را نشان می‌دهد و زیر کارت‌ها باز می‌شود.
- در مسیر، ساعت/سرعت و چهار بازه از یک بستهٔ روز کامل انتخاب می‌شوند. ETA، forecast نزدیک زمان رسیدن، خطر، تصمیم و تجهیزات همان serializer معتبر بکند هستند. موبایل ترتیب انتخاب روز/بازه، ساعت/سرعت، نقاط و خلاصه را حفظ می‌کند؛ نقاط بلند در اسکرول افقی خودشان می‌مانند. شروع «تغییر مسیر» در دسکتاپ با عنوان خلاصه روی یک خط عمودی است.
- ورود به صفحهٔ جدید به بالای هدر می‌رود؛ تغییر کنترل‌ها در همان صفحه اسکرول و focus را حفظ می‌کند. هنگام دریافت روز تازه، هویت صفحه و انتخاب‌گرها باقی می‌مانند و هوای روز قبلی نمایش داده نمی‌شود. پاسخ دیررس روز یا حساب قبلی کنار گذاشته می‌شود.
- اشتراک‌گذاری، PNG خلاصهٔ واقعی همان برنامه و URL حاوی slug، تاریخ ISO، ساعت و سرعت دارد. پیش‌نمایش، لینک قابل کلیک، کپی و دانلود واقعی فراهم‌اند. در HTTPS و مرورگر دارای file sharing، کلیک تازه share sheet سیستم را باز می‌کند؛ HTTP روی IP از fallback استفاده می‌کند.

## تغییرهای بکند و سازگاری

قراردادهای جدید `points/<slug>/forecast/day/` و `routes/<slug>/forecast/day/` در کنار endpointهای قبلی هستند. مسیر ۲۴ ساعت شروع × ۳ سرعت = ۷۲ برنامه را با همان محاسبات قبلی ارزیابی می‌کند؛ رکوردهای همهٔ نقاط و روزهای لازم پس از نیمه‌شب یکپارچه خوانده می‌شوند. مرز دسترسی روی تاریخ رسیدن و رکورد forecast اعمال می‌شود؛ tolerance اجازهٔ نشت هوای روز قفل‌شده نمی‌دهد.

`routes/` فهرست مستقل مسیرهای فعال است؛ فیلتر فهرست مقصدها اختیاری است. جست‌وجوی قدیمی بدون `include_routes=1` همان قرارداد مقصدها را دارد؛ حالت جدید، مسیرها و اطلاعات دستهٔ واقعی مقصدها را اضافه می‌کند. تعداد query فهرست مسیرها با prefetch کنترل می‌شود. حساب، پایان عضویت و روزهای مانده را به پاسخ قبلی اضافه می‌کند. provider در نبود apparent temperature رکورد آن ساعت را معتبر فرض نمی‌کند.

تغییر schema یا migration نداریم. SSR فهرست مسیرها و فونت جدید اکنون در production
فعال‌اند؛ robots و noindex فقط در runtime QA اعمال می‌شوند و sitemap و سیاست
canonical production حفظ شده‌اند. جزییات قرارداد و محدودیت کش در
[forecast-contract.md](api/forecast-contract.md) آمده است.

کش فقط در حافظهٔ همان مرورگر، private و حداکثر ۴۰ ورودی است؛ درخواست هم‌زمان تکراری ادغام می‌شود. ورود/خروج آن را پاک می‌کند. تغییر مشاهده‌شدهٔ زمان انتشار، سطح دسترسی یا پایان عضویت روزهای قبلی را نامعتبر می‌کند. TTL حداکثر ۵ دقیقه و کوتاه‌تر از مرز ساعت تهران یا پایان واقعی عضویت است؛ در انقضا، هوای قبلی از رابط کنار می‌رود و دسترسی دوباره بررسی می‌شود، در حالی که هویت و انتخاب‌گرهای صفحه باقی می‌مانند. تغییر Admin/ingest بیرون از مرورگر در refresh بعدی دیده می‌شود. پاسخ HTTP پیش‌بینی `private, no-store` و وابسته به Cookie است.

ابزار lint مستقلی در scripts فعلی پروژه تعریف نشده است؛ typecheck موجود اجرا شد. Python با dependencyهای Docker پروژه و PostGIS در دیتابیس **محلی جدا** بررسی شد. کاتالوگ commit پایه برای آزمون استفاده شد؛ کاتالوگ‌های تغییرکردهٔ قبلی کاربر (دارای مقادیر خارج از validator فعلی) اصلاح، حذف یا import نشدند. مرورگر Chromium و رابط‌های UI واقعی API محلی را مصرف کردند؛ تست‌های کامپوننت پاسخ کنترل‌شده دارند. دادهٔ تست و حساب QA محلی وارد repo یا سرور نمی‌شوند.

مقایسهٔ تصویری شامل فونت، رنگ، background، شفافیت، فاصله‌ها، آیکون، هدر موبایل، محل انتخاب مسیر، کارت‌ها و منوها بود. متن هوا، تاریخ، شمارش مقصدها و مسیرها، سطح دسترسی و تجهیزات از دادهٔ واقعی می‌آیند و با اعداد نمایشی بسته برابر نیستند؛ اخطار دادهٔ قدیمی/ناقص نیز در صورت لزوم حفظ می‌شود. بنابراین برابری pixel کامل با دادهٔ نمایشی ادعا نمی‌شود. تصاویر اجرای محلی در `.tmp/design-qa/screens/` باقی مانده‌اند.

## اندازه‌گیری سرعت

اعداد خام و نتیجهٔ HTTP/auth در [metrics.json](../design/qa/new-design/metrics.json) ثبت شده‌اند. مقایسهٔ مرورگر، checkout مستقل commit پایه و نسخهٔ جدید را با Chromium، Vite dev/StrictMode، همان API و PostGIS محلی اندازه گرفت. duration درخواست از `request.timing().responseEnd` و تعامل از کلیک تا دومین `requestAnimationFrame` است؛ سرور production اندازه‌گیری نشده است.

| سناریو | قبل | بعد |
|---|---|---|
| مقصد: ورود + چهار تغییر بازه + جزئیات | ۶ درخواست هوا | ۱ درخواست اولیه؛ تغییرها و جزئیات صفر درخواست |
| مسیر: ورود + سه تغییر سرعت | ۵ درخواست هوا | ۱ درخواست اولیه؛ تغییر سرعت صفر درخواست |
| مسیر: چهار بازه و تغییر ساعت در موبایل و دسکتاپ | هر انتخاب به fetch وابسته بود | صفر درخواست پس از بستهٔ اولیه؛ focus ساعت و اسکرول حفظ شد |
| روز امروز → دیروز → امروز | دوباره وابسته به fetch | یک درخواست برای روز تازه؛ بازگشت به امروز صفر درخواست |

کاهش تعداد درخواست در سناریوهای اندازه‌گیری‌شدهٔ مقصد **۸۳٪** و مسیر **۸۰٪** است. StrictMode نسخهٔ قبلی دو fetch اولیه داشت؛ این بخش از شمارش مخصوص dev است. حذف ۴ درخواست تغییر بازه و ۳ درخواست تغییر سرعت در production نیز برقرار است.

پیش از تغییر، هر درخواست بازهٔ مقصد حدود ۱۷۲ تا ۲۴۴ ms و تغییر سرعت حدود ۱۹۱ تا ۲۶۵ ms انتظار شبکه داشت. نمونهٔ نهایی تعامل محلی مقصد حدود ۱۰ تا ۴۶ ms و سرعت مسیر حدود ۸ تا ۷۹ ms بود؛ چهار بازهٔ مسیر در دو اندازه حدود ۱۰ تا ۷۱ ms. این‌ها زمان تا paint در سیستم توسعه هستند، نه تضمین latency گوشی یا سرور. با build/test هم‌زمان، نمونه‌های کندتر و یک پاسخ سرد حدود ۱٫۳ ثانیه نیز دیده شد.

| API؛ میانهٔ پنج اجرای گرم | قبل | بستهٔ کامل روز |
|---|---|---|
| مقصد | ۱۲۵٫۳۴ ms، ۱۴ SQL، ۳٫۴ KB gzip | ۱۳۸٫۲۱ ms، ۱۵ SQL، ۴٫۶ KB gzip |
| مسیر | ۱۲۹٫۲۶ ms، ۱۹ SQL، ۴٫۳ KB gzip | ۲۶۲٫۰۲ ms، ۱۳ SQL، ۱۲٫۸ KB gzip |

بستهٔ مسیر پیش از gzip حدود ۲۳۶ KB است و پاسخ اولیه CPU/حجم بیشتری دارد، چون همهٔ ۷۲ برنامه را آماده می‌کند. کاهش محسوس، حذف انتظار شبکه در انتخاب‌های بعدی است؛ سریع‌تر شدن پاسخ اولیه ادعا نمی‌شود. gateway QA gzip JSON دارد. خروجی build از نام فایل فعلی پروژه استفاده می‌کند؛ QA برای فایل JS/CSS ثابت `no-store` می‌فرستد تا build قبلی با API تازه مخلوط نشود.

## تحویل برای اجرای اپراتور

این طراحی پس از پایان QA در `main` ادغام و روی production فعال شده است. محیط
stage فعلاً متوقف است؛ راهنمای پاک‌سازی منابع باقی‌مانده در
[stage-deployment.md](stage-deployment.md) آمده است.

آزمون share sheet روی iOS/Android واقعی، انتخاب برنامهٔ مقصد و اعتماد certificate معتبر روی نام/IP عمومی، مرحلهٔ QA اپراتور است. کپی و ذخیرهٔ PNG بدون native sharing به‌صورت محلی بررسی شده‌اند.

## بررسی walking-v1

- ۸۵ آزمون بکندِ normalization، ingest، day bundle، تمام ۷۲ برنامهٔ مسیر،
  بازه‌ها و محدودیت دسترسی در PostgreSQL/PostGIS محلیِ جدا موفق شدند.
- ۲۸ آزمون مرزهای موتور هشدار و سازگاری باد، پس از تغییر نهایی موفق شدند.
- ۳۸ آزمون صفحات فرانت، typecheck و build موفق شدند.
- Chromium، مقصد و مسیر را در عرض‌های ۳۲۰، ۳۹۰ و ۱۴۴۰ و هر دو تم بررسی
  کرد: ۱۲ حالت، بدون خطای runtime و overflow افقی صفحه؛ رنگ عنوان جزئیات
  و مقادیر مؤثر، خنثی‌ماندن نام روز و جای‌گرفتن خلاصهٔ چندخطی بررسی شدند.
  پاسخ‌های مرورگر کنترل‌شده‌اند؛ این بررسی دستگاه واقعی یا سایت اصلی نیست.
- `makemigrations --check --dry-run` اختلافی با migration نسخه‌بندی‌شده نداشت.
- هیچ deploy، migration یا ingest روی سرور انجام نشد. کاتالوگ‌های تغییرکردهٔ
  کاربر وارد commit یا آزمون نشدند؛ آزمون‌های دیتابیس از fixtureهای HEAD استفاده کردند.
