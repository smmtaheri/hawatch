# پیش‌بینی هفته و تصمیم‌های اجرای v5

مقصد و مسیر از API داخلی زیر دریافت می‌شوند:

- `GET /api/v1/points/<slug>/forecast/week/`
- `GET /api/v1/routes/<slug>/forecast/week/`

پارامتر روز/ساعت/سرعت ندارند؛ پاسخ مربوط به امروز تهران و هفت روز بعد است.
انتخاب‌ها در همان داده انجام می‌شوند. محدودیت قبلی عضویت برای این هشت تاریخ برداشته
شده؛ API حساب، login و طراحی‌های login دست‌نخورده‌اند. عنوان UI «پیش‌بینی ۷ روزه» است.

## داده

دمای حسی و واقعی میانگین بازه، کمینه/بیشینه از دمای واقعی، باد و تندباد بیشینه،
بارش جمع بازه است. مقدار بارش ساعت t متعلق به ساعت پیش از t است؛ بازهٔ [a,b)
دماهای a تا پیش از b و بارش‌های بعد از a تا خود b را استفاده می‌کند. نبود داده
به `null` می‌انجامد؛ هیچ صفر ساختگی یا دمای جایگزین وجود ندارد.

در مسیر، هویت نقاط، رکوردهای ساعتی و شواهد تجهیزات یک‌بار می‌آیند؛ ۵۷۶ برنامه با
index به آن‌ها اشاره می‌کنند. زمان رسیدن همچنان از cumulative_minutes معتبر،
ضرایب ۱٫۲۵/۱/۰٫۸ و گردکردن موجود پنج دقیقه‌ای می‌آید. تطبیق هوا همان WeatherPoint،
نزدیک‌ترین ساعت در ±۹۰ دقیقه و تساوی با ترجیح ساعت زودتر است. timing ناقص یا
رسیدن خارج از پوشش داده، وضعیت نامشخص می‌گیرد. وضعیت تازگی از رکوردهای مصرف‌شده محاسبه می‌شود، نه ساعت‌های قدیمی صرفاً کمکی.
endpoint قدیمی روز برای سازگاری
مصرف‌کنندگان قدیمی باقی است؛ فرانت جدید از آن استفاده نمی‌کند.

فرود یک‌طرفه از مبدأ تا اولین رسیدن به مقصد استخراج شده، نه مجموع رفت‌وبرگشت.
پروفایل GPX با نمونه‌برداری ۵۰ متر و میانگین پنج نمونه نرم شده است. ۱۱۸ مسیر شواهد
قابل‌اعمال دارند و ۱۲۱ مسیر نامشخص‌اند. این اعداد مرجع GPX هستند و دقت میدانی ادعا
نمی‌کنند. script محلی پوشش origin/target، پیوستگی و ترتیب عوارض را بررسی می‌کند؛
partial/composite/technical و تعارض شواهد عدد عمومی تولید نمی‌کنند. اعمال روی DB
فقط در صورت تطابق کامل زنجیرهٔ canonical انجام می‌شود.

## کش و درخواست‌ها

JS/CSS در `/static-assets/<frontend-hash>/` و فایل‌های public مانند فونت و تصویر
در `/static-public/<public-hash>/` با یک سال immutable سرو می‌شوند؛
نسخهٔ public فقط با تغییر فایل‌های public عوض می‌شود؛ تغییر کد آن را عوض نمی‌کند.
نسخهٔ فرانت از کد/وابستگی‌های فرانت است؛ انتشار صرفاً بکند آن را عوض نمی‌کند.
فونت و تصاویر همان فایل‌های پیشین‌اند. URL نسخه‌دار از HTML سرور و build فرانت
یکسان ساخته می‌شود. مرورگر و CDN می‌توانند این فایل‌ها را مشترک cache کنند.

پاسخ هفته ETag و کش HTTP خصوصی مرورگر تا دو دقیقه دارد (در نیمه‌شب کوتاه
می‌شود). مقایسهٔ `If-None-Match` برای ETag قوی و weak (پس از gzip) یکسان است؛ دادهٔ ثابت با `304` بدون بدنه و دادهٔ تغییرکرده با `200` برمی‌گردد. `CDN-Cache-Control: no-store` و `Surrogate-Control: no-store` و
`Cache-Control: private` کش مشترک هوا را منع می‌کنند؛ gateway نیز این سیاست را
حفظ می‌کند. CDN فقط برای فایل‌های ثابت است؛ پنل CDN نباید این هدرها را override
کند. کش قدیمی عمومی دامنه پس از انتشار روی production باید یک بار purge شود.

فهرست ثابت اولیهٔ ۱۰۰ مقصد در `apps/api/fixtures/week_cache_points.json` است؛
این انتخاب تحریریه از مقصدهای شناخته‌شده است، نه آمار واقعی Search Console.
پس از هر ingest موفق/partial، این مقصدهای فعال عمومی و اولین Route فعال
هرکدام با همان ترتیب صفحه (`sort_order`, سپس `slug`) در Redis گرم می‌شوند.
مقصد point-only مسیر ساختگی نمی‌گیرد؛ مسیر مشترک فقط یک‌بار گرم می‌شود.

بازدید صفحه با POST داخلی `/api/v1/{points|routes}/<slug>/forecast/visit/` ثبت
می‌شود و آن صفحه را تا آخرین بازدید +۴۸ ساعت وارد همین چرخه می‌کند؛ پنجره‌ها
جمع نمی‌شوند. فقط نوع صفحه، slug و مهلت در PostgreSQL نگهداری می‌شوند؛ دادهٔ
کاربر، IP و اطلاعات هوا در این جدول نیست. بازشدن صفحه/refresh بازدید است؛
انتخاب روز/ساعت/سرعت، focus، polling و گرم‌سازی بازدید نیستند. GET مستقیم API
هم بازدید ثبت نمی‌کند. ردیف‌های منقضی در گرم‌سازی بعدی حذف می‌شوند و دیگر
گرم نمی‌شوند. Redis eviction یا restart فهرست ۴۸ساعته را از بین نمی‌برد.

Redis فقط پاسخ سریال‌شدهٔ فشردهٔ هفته را نگه می‌دارد؛ schema کش `week-4` است و به commit ظاهر وابسته نیست.
در miss پاسخ از دیتابیس ساخته می‌شود. TTL تا اجرای بعدی همان scheduler
(`HAWATCH_INGEST_SCHEDULE`، پیش‌فرض ۶ساعته) یا نیمه‌شب، هرکدام زودتر است.
عدد مستقل سه/شش ساعت برای کش نداریم. ingest جدید و ویرایش catalog بعد از
commit revision را عوض می‌کنند؛ پاسخ نسل قدیم حتی قبل از پایان TTL دوباره
خوانده نمی‌شود. ingest ناموفق داده را تازه نمی‌کند؛ وضعیت تازگی قبلی حفظ
می‌شود. تغییر bulk خارج از service باید `invalidate_week_cache` را صدا بزند.

بار اول: فایل‌های ثابت از مرورگر/CDN، هفته از Redis یا در miss از DB.
هیچ درخواست GET هوا به provider متصل نیست. کل هفتهٔ مقصد/مسیر یک پاسخ دارد؛
کنترل‌ها درخواست هوا ندارند. حافظهٔ فرانت سه صفحه را حداکثر دو دقیقه نگه
می‌دارد؛ refresh از کش HTTP خصوصی مرورگر یا API است. IndexedDB/localStorage
هوا نداریم. Redis سقف ۱۲۸MB و LRU دارد؛ فشرده‌سازی پاسخ‌ها فشار حافظه را کم
می‌کند، ولی تضمین عدم eviction زیر بار نامحدود نیست.

## تجهیزات، سیاست اولیهٔ قابل بازبینی

این‌ها مکمل وسایل معمول‌اند و علت/نقطه/زمان دارند؛ altitude یا فصل به‌تنهایی
تجهیزات تعیین نمی‌کند و فقط از هوای پیش‌بینی‌شدهٔ نقاط پیمایش استفاده می‌شود.

| شاهد پیش‌بینی | تأکید تجهیزات |
| --- | --- |
| دمای حسی ≤۱۰°C | پلار |
| دمای حسی ≤۰°C | کاپشن عایق، دستکش عایق، کلاه گرم |
| دمای حسی ≤−۱۰°C | دستکش پر/میتن عایق |
| باد ≥۳۰ یا تندباد ≥۵۰ km/h | وینداستاپر؛ همراه سرما کلاه طوفان |
| بارش | پانچو یا هاردشل؛ همراه باد/برف هاردشل و شلوار ضدآب |
| برف پیش‌بینی‌شده | گتر؛ همراه باد گوگل مناسب کولاک |
| UV ≥۳، فقط اگر داده دارد | عینک UV، ضدآفتاب و پوشش محافظ |

هاردشل، پیشنهاد تکراری وینداستاپر/پانچو را حذف می‌کند. کفش معمول، غذا، نوشیدنی،
کوله و توصیه‌های عمومی حذف شده‌اند. UV اکنون از hourly provider درخواست می‌شود؛
مقدار unavailable همچنان نامشخص می‌ماند. طناب/کلنگ/کرامپون از برف هواشناسی به‌تنهایی
استنتاج نمی‌شوند؛ دادهٔ وضعیت سطح، برف انباشته و ماهیت فنی مسیر هنوز کافی نیست.
آستانه‌های جدول سیاست اولیهٔ explicit برای بازبینی کاربرند؛ ارزیابی پزشکی/ایمنی
یا اعتبارسنجی میدانی ادعا نشده است. کل نقاط مسیر، نه فقط خطرناک‌ترین نقطه، بررسی
می‌شوند؛ پوشش پیوستهٔ زمین بین waypointها از این forecast قابل استنتاج نیست.

## اشتراک

`POST /api/v1/shares/` با route/date/start_hour/speed لینک opaque `/p/<code>`
می‌سازد. ساعت عدد صحیح ۰..۲۳ و اعتبار ۳۰ روز است؛ weather snapshot ذخیره نمی‌شود.
برنامهٔ گذشته به امروز همان مسیر و همان ساعت/سرعت هدایت می‌شود و پیام گذشته‌بودن
برنامه روی صفحه دیده می‌شود. عکس PNG شامل تمام نقاط و خلاصه است؛ تجهیزات، کنترل
و URL داخل عکس نیست. تصویر در مرورگر ساخته می‌شود و خروجی بستهٔ دمو وارد runtime
نشده است.

## ظاهر و بررسی

کد geometry/icon/chart نسخهٔ v5 با ثبت provenance استفاده شده؛ محاسبات دمو حذف
شده‌اند. قراردادهای تصویری original بدون تبدیل در `design/screens/forecast-v5/`
هستند. اندازه‌ها/وزن‌های تصمیم‌گرفته‌شده در `features/week/agreed.css` از reference
جداست. خانواده و فایل فونت همان Vazirmatn فعلی نسخهٔ سایت مانده و Estedad/OFL نیز
حذف یا تغییر نکرده‌اند. پنل‌ها scroll داخلی دارند و صفحه overflow افقی ندارد.

سنجش محلی با دادهٔ synthetic، شاهد کارکرد کد است؛ عدد سرعت production/CDN نیست.
پس از deploy استیج: مقصد، مسیر کوتاه و بلند، cold/warm، gzip payload، زمان سرور
و نمایش موبایل روی شبکهٔ واقعی باید مقایسه شوند.

نتایج تست، حجم پاسخ و زمان‌های محلی در [گزارش بررسی](week-forecast-qa.md) ثبت شده‌اند.

## اصلاحات پس از بررسی استیج

فرود در خروجی جزئیات مسیر نیز ارسال می‌شود. فاصلهٔ تجمعی نقاط از طول واقعی GPX
در زنجیرهٔ مرتب نقاط استخراج و برای پروفایل‌های ناقص در `segment_distance_m`
ثبت می‌شود؛ پروفایل کامل قبلی حفظ می‌شود. نقطهٔ آغاز صفر است؛ فاصلهٔ سایر نقاط
بدون ترک معتبر همچنان نامشخص می‌ماند. زمان‌بندی و مسافت کلی قبلی تغییر نمی‌کنند.

متن مدت مسیر کنار زمان رسیدن در ستون قبلی قرار دارد؛ اندازهٔ آن ۱۵px و در موبایل
زیر ۳۶۰px برابر ۱۴px است و وزن bold حفظ می‌شود. در موبایل
فاصلهٔ عنوان دمای حسی تا نمودار کمتر شده؛ مقادیر و مقیاس داده تغییر نکرده‌اند.
دکمه‌های اشتراک/ذخیره عرض و ارتفاع برابر دارند؛ زیر عرض ۳۶۰ دو ردیف تمام‌عرض
می‌شوند تا متن شکسته نشود. رفتار اشتراک در مرورگر پشتیبانی‌نشده دست‌نخورده است.

کلید کش payload هفته شامل نسخهٔ build است؛ پاسخ worker قدیمی در زمان دیپلوی
نمی‌تواند کش worker جدید را پر کند.

## بازگرداندن نام وضعیت هوا

با تصمیم جدید کاربر، نام فارسی وضعیت هوا زیر آیکون مقصد، نقطهٔ مسیر و عکس
اشتراک نمایش داده می‌شود. متن از condition همان رکورد/بازهٔ منتخب API می‌آید؛
برای پاسخ نسخهٔ قدیمی، نام متناظر weather_code جایگزین است. تجمیع و انتخاب
رکورد نماینده تغییر نکرده‌اند. متن معمولی ۱۲px دسکتاپ و ۱۱px موبایل است؛
خانوادهٔ فونت و وزن عنوان‌ها تغییر نکرده‌اند. نوار آیکون مقصد ۱۸px بلندتر شده؛ ارتفاع بخش عنوان/آیکون مسیر ۱۹۸px
در دسکتاپ و ۱۷۸px در موبایل و عکس خروجی ۱۹۴px است، تا متن با نمودار تداخل
نداشته باشد. هیچ درخواست هواشناسی اضافه نمی‌شود.


## پاسخ مهمان و آماده‌سازی نمودار

`GET /api/v1/auth/me/` برای مهمان `200 {"authenticated":false}` و هدر private/no-store
می‌دهد؛ وضعیت مهمان خطا نیست و CDN نباید آن را به HTML خطا تبدیل کند. پاسخ عضو
و منطق login/logout تغییری نکرده‌اند. این پاسخ عمومی کش نمی‌شود.

renderer مسیر snapshot همان روز/ساعت/سرعت را برای هدر، نمودار و خلاصه دوباره
مصرف می‌کند؛ فقط آخرین snapshot نگه داشته می‌شود. تجهیزات هنگام بازکردن بخش
تجهیزات آماده می‌شوند و با تغییر برنامه مجدداً محاسبه می‌شوند؛ دادهٔ هفته یا
محاسبات زمان رسیدن تغییری نکرده‌اند. اندازه/وزن فونت و تصاویر اصلی تغییر نکرده‌اند.

## سیستم طراحی مشترک

ظاهر پیش‌بینی هفته از [سیستم طراحی جاری](../design/system/design-system.md) می‌آید: سطح و رنگ نسخهٔ قبلی سایت مبناست؛ اندازه/وزن و هندسهٔ تأییدشدهٔ هفته حفظ می‌شوند. عکس viewport ثابت و مشترک، بدون بریدگی در جزئیات و تجهیزات باز است. توکن مستقل `.66/.64` یا blur کارت پیش‌بینی نداریم. مرجع تصاویر اجرای جاری `design/screens/current/` است.
