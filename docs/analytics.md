# آمار بازدید داخلی هواچ

## اتصال پایه به GA4

آمار داخلی بالا مرجع مستقل هواچ باقی می‌ماند. GA4 فقط برای page viewهای عمومی
استفاده می‌شود و رویداد اختصاصی هواچ به آن ارسال نمی‌کند. تنظیم runtime با
متغیر عمومی `GA4_MEASUREMENT_ID` انجام می‌شود؛ مقدار فعلی stream برابر
`G-B9F7GYQ0X8` است. آن را در `.env` کنار فایل Compose بگذارید:

```dotenv
GA4_MEASUREMENT_ID=G-B9F7GYQ0X8
```

در production این فایل روی سرور، معمولاً `/root/hawatch/.env`، تنظیم می‌شود.
همان متغیر به‌صورت runtime از طریق `env_file` به API/Django می‌رسد و Compose آن
را هنگام build وب به `VITE_GA4_MEASUREMENT_ID` می‌دهد. Django شناسه را در HTML
صفحات SSR می‌گذارد؛ bundle هم آن را برای مسیرهای عمومی‌ای که از پوستهٔ استاتیک
React می‌آیند می‌خواند. اسکریپت deploy فایل `.env` موجود را جایگزین نمی‌کند؛ در
سرورهای فعلی این خط باید پیش از deploy کد اضافه شود تا هم image وب با شناسه ساخته
شود و هم API آن را هنگام شروع بعدی بخواند. در توسعهٔ محلی می‌توان متغیر را خالی
گذاشت. مقدار غایب/نامعتبر بی‌صدا GA4 را غیرفعال می‌کند.

GA4 فقط در build production، روی `https://hawatch.ir` یا
`https://www.hawatch.ir` و بیرون از preview فعال می‌شود. Vite dev server،
localhost، HTTP، preview/QA و صفحات خارج از مسیرهای عمومی مجاز هیچ اسکریپت یا
درخواستی به Google نمی‌فرستند.

React Router مسیرهای عمومی خانه، فهرست مقصدها/مسیرها، صفحهٔ اشتراک، نقطه و مسیر
را دنبال می‌کند؛ صفحهٔ login که به خانه redirect می‌شود و صفحات ناموجود در این
allowlist نیستند. تغییر query یا hash به‌تنهایی
page view نیست. مسیر فقط بعد از آماده‌شدن عنوان React ثبت می‌شود. HTML SSR صفحهٔ
مستقیم عنوان آماده را از قبل دارد؛ صفحهٔ نقطه/مسیر در ناوبری SPA تا دریافت نام
واقعی همان مقصد صبر می‌کند. بازکردن مستقیم، refresh و هر انتقال واقعی مسیر از
جمله Back/Forward یک page view می‌سازند. تکرار effect در React StrictMode و
تغییر query/filter با coordinator هر مسیر حذف می‌شود. در اولین page view، URL از
origin و pathname عمومی به‌علاوهٔ فقط پارامترهای استاندارد و allowlist‌شدهٔ UTM
ساخته می‌شود؛ سایر queryها و hash هرگز فرستاده نمی‌شوند. مقدار UTM خالی، بیش از
۱۰۰ نویسه، دارای کنترل‌کاراکتر، ایمیل، موبایل ایرانی، شمارهٔ بین‌المللی با `+`
یا credential صریح حذف می‌شود. تاریخ در نام کمپین و شناسهٔ عددی عادی معتبرند؛
فیلتر عنوانِ متن آزاد برای UTM استفاده نمی‌شود. برچسب کمپین نباید حاوی اطلاعات
شخصی کاربر باشد؛ یک عدد بدون زمینه را نمی‌توان قطعی از شناسهٔ کمپین تفکیک کرد.
Referrer بیرونیِ بارگذاری اول فقط به origin محدود می‌شود تا منبع ورود حفظ شود،
بدون ارسال مسیر یا query احتمالیِ شخصی؛ referrer هم‌دامنه فقط از مسیر عمومی و
بدون query/hash ساخته می‌شود. page viewهای بعدی URL پاک و مسیر قبلی داخلی را به
عنوان referrer مجازی می‌گیرند. عنوان از `document.title` همان لحظهٔ آماده‌شدن
خوانده می‌شود و ایمیل، شماره و عبارت‌های credential-like از آن حذف می‌شوند.

در Google tag روی GA Signals و ad personalization سیگنال خاموش‌اند. کد
`send_page_view: false` را به `config` می‌دهد و `page_view` را دستی ثبت می‌کند.
در کد فعلی پروژه cookie-consent/CMP یا تنظیم Consent Mode پیدا نشد؛ این اتصال
موجودیت آن را تغییر نمی‌دهد. اگر سیاست محصول/حوزهٔ فعالیت به رضایت پیشینی نیاز
دارد، باید CMP/Consent Mode جداگانه طراحی شود، نه اینکه این پیاده‌سازی را به‌جای
رضایت تلقی کنیم.

### تنظیمات پنل GA4

برای جلوگیری از تکرار و جمع‌آوری URLهای queryدار، در **Admin → Data streams →
web stream هواچ → Enhanced measurement** کل Enhanced Measurement را فعلاً خاموش
کنید. کد هواچ page view را دستی می‌فرستد؛ GA4 همچنان رویدادهای پایهٔ خودش مثل
`session_start`، `first_visit` و `user_engagement` را طبق رفتار معمول ثبت می‌کند.
بعداً اگر scroll/click/download هم خواستید، می‌توانیم گزینه‌های لازم را جدا
فعال کنیم، اما ثبت خودکار Page views و به‌ویژه **Page changes based on browser
history events** نباید همزمان با ثبت دستی فعال باشد. این قاعده با راهنمای رسمی
Google برای page view دستی در SPA هم‌راستاست.

### تأیید پس از deploy

1. در سرور، خط `GA4_MEASUREMENT_ID=G-B9F7GYQ0X8` را به `.env` اضافه و deploy
   عادی کد را اجرا کنید؛ این متغیر را در فایل‌های frontend یا HTML ثابت نگذارید.
2. در Chrome DevTools → Network، فیلتر `gtag/js` را بزنید و صفحهٔ عمومی را
   با یک UTM آزمایشی باز کنید. باید حداکثر یک بار `gtag/js?id=G-B9F7GYQ0X8`
   بارگیری شود؛ درخواست `collect` اول باید `en=page_view`، `dl` شامل فقط UTMهای
   مجاز و `dr` برابر origin منبع بیرونی (در صورت وجود) داشته باشد. queryهای
   planner، hash و مسیر/query referrer بیرونی نباید در payload باشند. page viewهای
   SPA باید `dl` بدون query و `dr` برابر مسیر عمومی قبلیِ بدون query باشند.
3. برای DebugView، از **Tag Assistant → Troubleshoot tag** حالت debug را فقط
   برای مرورگر خودت فعال کن و در GA4 **Admin → DebugView** برو. DebugView باید
   برای خانه → مقصدها → نقطه → مسیر، و نیز Back/Forward یک `page_view` با
   `page_title` و `page_location` همان صفحه نشان دهد؛ تغییر تاریخ/ساعت/سرعت
   نباید event جدید بسازد. Refresh باید یک event جدید برای بارگذاری جدید بسازد.
4. در **Reports → Realtime** بعد از چند ثانیه همان session و page viewها را
   ببینید. تأیید دریافت واقعی در DebugView/Realtime نیازمند دسترسی شما به
   property GA4 است؛ تست کد به‌تنهایی تحویل داده‌شدن event به Google را اثبات
   نمی‌کند.

اگر Google، افزونهٔ مسدودکننده یا شبکه درخواست را رد کند، خطای script به‌صورت
بی‌صدا مدیریت می‌شود، صف موقت پاک می‌شود و تلاش مجدد خودکار انجام نمی‌شود؛ UI و
درخواست‌های Open-Meteo وابستگی‌ای به بارگیری GA ندارند.

## گزارش داخلی بازدید و منبع ورود

گزارش داخلی مستقل از GA4 در همان URL قبلی باقی می‌ماند:
`/admin/analytics/pageviewevent/overview/`. دسترسی فقط برای superuser فعال است؛
HTML و CSV خصوصی، `no-store` و `noindex` هستند. API عمومی فقط POST ثبت رویداد
دارد و هیچ endpoint عمومی برای خواندن آمار ساخته نشده است.

### تعریف سنجه‌ها و بازه‌ها

- «بازدید نقاط و مسیرها» همان Page View صفحات canonical فعال است. ورود به هوم
  یا Hub به‌عنوان بازدید یک قله یا مسیر ثبت نمی‌شود.
- «ورود به کل سایت» تعداد نشست‌های آغازشده در بازه را نشان می‌دهد؛ شامل کسی که
  فقط هوم را دیده و خارج شده هم هست. شمارش نشست در گزارش صفحات، تعداد نشست‌های
  متمایزی است که در بازه آن صفحات را دیده‌اند، حتی اگر نشست زودتر شروع شده باشد.
- بازدیدکنندهٔ یکتای کل بازه با distinct همان بازه محاسبه می‌شود. جمع یکتای
  گروه‌ها/روزها/صفحات، یکتای کل نیست؛ یک نفر می‌تواند عضو چند گروه باشد.
- ۲۴ ساعت، ۷ روز و ۳۰ روز، بازهٔ شناور تا لحظهٔ گزارش‌اند؛ از نیمه‌شب شروع
  نمی‌شوند. bookmark قبلی `range=today` اکنون معادل ۲۴ ساعت اخیر است.
- N روز از ۱ تا ۳۶۵۰۰ و تاریخ/ساعت دلخواه پشتیبانی می‌شود. تاریخ‌های بدون
  offset به ساعت تهران خوانده می‌شوند؛ مرز شروع شامل و مرز پایان خارج بازه است.
- پایان گزارش برای صفحه‌بندی، drill-down و CSV در `until` ثابت می‌شود؛ Apply
  با همان مقدار، همان snapshot زمانی را می‌گیرد. پاک‌کردن فیلترها زمان را تازه
  می‌کند. زمان سرور مرجع است و پایان آینده به اکنون محدود می‌شود.

گزارش با ترکیب منبع، نوع صفحه، نحوهٔ رسیدن، صفحهٔ قبلی، landing، کمپین، دامنهٔ
ارجاع و slug فیلتر می‌شود. تفکیک بر اساس صفحه، منبع، روش رسیدن، صفحهٔ قبلی،
صفحهٔ ورود، کمپین، دامنه و ساعت/روز ممکن است. جدول، نمودار میله‌ای، جزئیات
قابل‌کلیک و CSV از همان فیلترها استفاده می‌کنند. جزئیات ورودها در بخش
`Visit sessions` ادمین هم در دسترس است. صفحات آرشیوی دارای رویداد از جمع حذف
نمی‌شوند و صفحات بدون بازدید در گزارش صفحهٔ بدون فیلتر باقی می‌مانند.

### منبع ورود و ناوبری

شناسهٔ ناشناس مرورگر در localStorage نگه‌داری و فقط HMAC آن در DB ذخیره می‌شود؛
IP، User-Agent، کوکی ورود، عبارت جست‌وجوی داخلی یا URL کامل بیرونی ذخیره نمی‌شود.
اگر storage مسدود باشد، شناسه در حافظهٔ همان document ثابت می‌ماند؛ refresh،
پاک‌کردن storage یا مرورگر/دستگاه دیگر می‌تواند شناسهٔ جدید بسازد. این آمار
تشخیص قطعی هویت انسان یا مقاومت در برابر جعل عمدی شناسه نیست.

نشست با ۳۰ دقیقه فاصله میان navigationهای عمومی تازه می‌شود و بین تب‌هایی که
localStorage مشترک دارند قابل استفاده است. منبع، landing و کمپین در طول نشست
ثابت‌اند؛ رفتن از هوم به سرچ، منبع اولیهٔ گوگل/تلگرام را تغییر نمی‌دهد. این
تعریف نشست بر پایهٔ navigation است و ادعای تطابق کامل با تعریف GA4 ندارد.

اولویت تشخیص منبع: UTM معتبر، سپس دامنهٔ referrer، سپس «مستقیم/نامشخص».
UTM شاهد برچسب لینک است و اثبات هویت پلتفرم کلیک‌کننده نیست؛ روش تشخیص در
`source_evidence` نگه داشته می‌شود. گوگل، بینگ، اینستاگرام، تلگرام و referral
شناخته می‌شوند. لینک‌های منتشرشدهٔ بیو/استوری/کانال باید `utm_source`،
`utm_medium` و `utm_campaign` استاندارد داشته باشند. referrer ممکن است توسط
مرورگر یا اپ حذف شود؛ منبع غایب حدس زده نمی‌شود. در `/p/<code>` فقط همین سه
برچسبِ معتبر به مقصد منتقل می‌شوند؛ تاریخ، ساعت و سرعت ذخیره‌شدهٔ برنامه تغییر
نمی‌کند و query دلخواه/خصوصی کپی نمی‌شود.

نمونهٔ لینک کانال: `https://hawatch.ir/?utm_source=telegram&utm_medium=social&utm_campaign=channel`.
برای بیوی اینستاگرام می‌توان `utm_source=instagram` و `utm_campaign=bio` گذاشت؛
این برچسب‌ها باید هنگام انتشار لینک اضافه شوند.

ناوبری داخلی جداست: سرچ داخلی (کلیک عادی یا Enter)، هوم، Hubها، نقطه، مسیر و
Back/Forward. در تب جدید که محل کلیک قطعی منتقل نمی‌شود، سرچ حدس زده نمی‌شود.
URL داخلی هیچ برچسب analytics نمی‌گیرد؛ state برگشت، planner، hash، اسکرول،
canonical و policy فعلی query/noindex/cache تغییر نمی‌کنند. تاریخ/ساعت/سرعت،
polling و تغییر تم، Page View تازه نمی‌سازند. هر پیمایش واقعی، از جمله
نقطه→هوم→همان نقطه و Back/Forward، ثبت می‌شود؛ effect تکراری دو بار نمی‌شمارد.

برای نقطه/مسیر، همان POST موجود با context محدود غنی می‌شود. در اولین صفحهٔ
عمومی غیرنقطه/مسیر، یک POST سبک برای آغاز نشست ارسال می‌شود؛ برای هر کلیک یا
تایپ درخواست جدا نداریم. metadata اختیاری است؛ payload قدیمی معتبر می‌ماند،
metadata خراب یا غایب مانع ثبت اصل بازدید نیست و بدنه همچنان زیر ۲KB می‌ماند.
خطای شبکهٔ analytics مستقل از نمایش و دریافت هواست. staff، bot و rate limit
قبلی حفظ شده‌اند.

### تاریخچه و عملکرد

از migration جدید، رخدادهای دقیق نگه داشته می‌شوند تا N روز دلخواه و یکتای
واقعی بازه ممکن باشد. فرمان maintenance قبلی `cleanup_analytics_retention`
سازگار و غیرتخریبی باقی می‌ماند و دیگر رخدادها را حذف نمی‌کند. رشد حجم جدول
باید پایش شود؛ حذف آینده نیازمند طرحی است که دقت و پوشش گزارش را صریح کند.

تجمیع‌های ماهانهٔ قبلی تغییر نمی‌کنند. فقط در کل زمان بدون فیلتر منبع/ناوبری
در جمع و جدول می‌آیند؛ یکتای آن بخش تقریبی است و نشست ندارد. در تفکیک‌های
دیگر ردیف «تاریخچهٔ ماهانه؛ تفکیک موجود نیست» جداست. بازهٔ دلخواهی که به دادهٔ
حذف‌شدهٔ گذشته برمی‌خورد، هشدار پوشش ناقص می‌گیرد. `AnalyticsCoverage` مرز
قابل اتکای تاریخچهٔ دقیق و شروع قابلیت attribution را در migration ثبت می‌کند؛
برای گذشته source ساختگی تولید نمی‌شود.

فقط بازهٔ انتخابی query می‌شود؛ برای هر ردیف query جدا ساخته نمی‌شود. صفحه‌بندی
۵۰ ردیفی، خروجی حداکثر ۱۰۰۰۰ گروه و timeout هر query گزارش (پیش‌فرض ۳ ثانیه)
از اشغال طولانی منابع عمومی جلوگیری می‌کنند. timeout در transaction محلی اعمال
و سپس بازگردانده می‌شود؛ تنظیم connection عمومی تغییر نمی‌کند. CSV بزرگ باید
با بازه/تفکیک محدودتر گرفته شود. گزارش کش Redis ندارد تا ترکیب‌های دلخواهِ
فیلتر، کش مشترک آب‌وهوا را اشغال نکنند.

محبوب‌های هوم با **بازدیدکنندهٔ یکتای هر مقصد در هفت تاریخ تقویمی اخیر تهران**
رتبه‌بندی می‌شوند؛ صد کلیک یک visitor در این بازه یک رأی است. route، waypoint
فنی و رویداد آغاز نشست در رتبه اثر ندارند. window، tie-break و کش پنج‌دقیقه‌ای
هوم با فیلترهای گزارش تغییر نمی‌کنند. محدودیت شناسهٔ مرورگری بالا همچنان برقرار است.

### انتشار و بازگشت

ابتدا migration افزایشی `analytics.0003`، سپس API و فرانت منتشر شوند؛ کلاینت
قدیمی و تب باز همچنان معتبرند. migration هیچ رویداد یا مقصد/مسیر را حذف نمی‌کند.
این کار نیازمند تغییر DNS/CDN یا sync کاتالوگ نیست؛ کاتالوگ‌های ناتمام checkout
نباید همراه انتشار analytics سینک شوند.

`ANALYTICS_ATTRIBUTION_ENABLED=false` در تنظیمات API ثبت context/نشست تازه را خاموش
می‌کند ولی اصل Page View و خواندن تاریخچه حفظ می‌شوند. برای build فرانت،
`VITE_ANALYTICS_ATTRIBUTION_ENABLED=false` نیز ثبت ورود/context را خاموش می‌کند.
`ANALYTICS_REPORT_TIMEOUT_MS` بودجهٔ query را بین ۱۰۰ و ۳۰۰۰۰ میلی‌ثانیه تنظیم
می‌کند. بازگشت معمول با خاموش‌کردن قابلیت/نسخهٔ قبلی کد است؛ schema و داده‌های
تازه برای rollback پاک نشوند. انتشار روی سایت زنده نیازمند deploy جداگانه است.
