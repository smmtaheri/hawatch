## تست و ساخت

- فرانت: ۱۸۳ تست در ۱۵ فایل، همگی موفق؛ TypeScript و build تولیدی Vite و Docker موفق.
- بک‌اند: اجرای گستردهٔ مرتبط ۱۱۹ تست داشت؛ ۱۱۷ موفق بود و دو انتظار قدیمی اصلاح شد. اجرای نهایی ۲۱ تست هفته، استیج، snapshot و آستانهٔ باد همگی موفق بود.

## داده و کش

- انتقال JSONL روی دو دیتابیس محلی مستقل بررسی شد: ۴۲ WeatherPoint، ۷ Route و ۱۰۰۸۰ رکورد هوا منتقل شدند؛ کاربران مقصد صفر ماندند. این تست از دادهٔ دمو استفاده کرد، نه پروداکشن.
- Redis واقعی با سقف ۱۲۸MB استفاده شد. cache HIT در فرآیند دوم بدون کوئری دیتابیس بررسی شد.
- API عمومی: ETag و HTTP cache دو دقیقه؛ asset نسخه‌دار: یک سال immutable. وجود HIT واقعی CDN فقط بعد از دیپلوی و عبور از دامنه/CDN قابل تأیید است.

## سرعت محلی

دادهٔ دمو، Docker و میزبان مشترک؛ زمان‌ها آزمون بار یا عدد سرعت استیج نیستند. Seed پیش از شروع تایمر آماده شد. API قدیمی فقط یک روز دارد؛ API جدید امروز و هفت روز آینده و همهٔ ساعت/سرعت‌ها را می‌دهد.

## ظاهر و تعامل

بررسی Chromium در عرض‌های ۳۲۰، ۳۹۰، ۷۶۸ و ۱۴۴۰، هر دو تم و مقصد/مسیر: نبود overflow افقی، خطای JS و asset گمشده بررسی شد. انتخاب ساعت/سرعت، بازکردن تجهیزات و جزئیات از همان پاسخ انجام شدند. فونت فعلی حفظ شد. تصاویر مرجع اصلی بدون تبدیل در `design/screens/forecast-v5/` هستند.

اشتراک مسیر ۱۰نقطه‌ای با ساعت ۲۳ و سرعت آهسته در هر دو تم، لینک کوتاه با redirect درست و PNG تمام نقاط/خلاصه بررسی شد. خروجی PNG محلی تولید شده و قرار نیست به‌عنوان تصویر محصول بارگذاری شود.

برای بررسی پس از دیپلوی از لوکال: `python3 scripts/check-week-cache.py --base-url http://202.133.89.120:5050`؛ برای اثبات CDN، همین بررسی باید با دامنه‌ای که از CDN عبور می‌کند تکرار شود.

## اصلاح کش فرود و بازگشت مدت مسیر به ستون قبلی

روی استیج a2b7d41، API جزئیات مسیر فرود `0` داشت، ولی پاسخ HIT هفته حتی کلید
`descent_m` نداشت. worker قبلی در فاصلهٔ آماده‌سازی تا restart، کش عمومی قدیمی را

نیاز خط بعدی می‌آید. در ۳۲۰، ۳۹۰ و ۱۴۴۰ و هر دو تم، هم‌ردیفی زمان رسیدن/مدت،
فاصلهٔ متن از حاشیه، نمایش مقدار صفر فرود و نبود overflow بررسی شدند.

## نام فارسی وضعیت هوا زیر آیکون‌ها

۱۸۵ تست فرانت، ۱۴ تست API هفته و تست API مقصد پس از افزودن assertion متن
وضعیت موفق شدند؛ build فرانت نیز موفق است. متن فارسی از condition رکورد
نمایندهٔ API می‌آید؛ fallback پاسخ قدیمی بر اساس weather_code است.

Chromium محلی در عرض‌های ۳۲۰، ۳۹۰ و ۱۴۴۰، هر دو تم، مقصد و مسیر و پیش‌نمایش
اشتراک بررسی شد: بدون خطای JavaScript یا overflow صفحه، متن‌ها زیر آیکون،
دکمه‌ها هم‌اندازه، مدت/رسیدن هم‌ردیف و صفر فرود قابل مشاهده‌اند. سناریوی دوم
متن «رعدوبرق با تگرگ» را به دادهٔ خوانده‌شده تزریق کرد و نبود تداخل با نمودار
را اندازه گرفت؛ این سناریو پیش‌بینی واقعی رعدوبرق نیست. ارتفاع عنوان‌های مسیر
به‌صورت صریح با specificity کافی رزرو شده تا قاعدهٔ responsive قبلی آن را
کوچک نکند. فونت مرجع موجود و اندازه/وزن نام نقاط و ساعت‌ها حفظ شده‌اند.

پاسخ‌های هوا فقط از API استیج خوانده و در مرورگر محلی mock شدند؛ هیچ POST
اشتراک یا تغییری روی سرور انجام نشد. تصاویر جدید در
`design/screens/forecast-v5/implementation/weather-labels/` و اندازه‌گیری در
`week-forecast-weather-labels-check.json` و `week-forecast-weather-labels-long-check.json`
هستند. گزارش snapshot کامل‌بودن داده و پیش‌نیازهای پروداکشن در
[audit آمادگی main](audits/forecast-readiness-2026-10-09.md) ثبت شده است.

## چرخهٔ کش مقصدهای ثابت و بازدیدهای ۴۸ساعته

- فهرست ثابت اولیهٔ ۱۰۰ مقصد شناخته‌شده در `fixtures/week_cache_points.json`،
  همراه اولین مسیر هر مقصد طبق ترتیب خود صفحه؛ فایل قابل‌ویرایش و فاقد ادعای
  رتبه‌بندی واقعی Google Search Console است. مسیر مشترک deduplicate می‌شود.
- بعد از ingest موفق/partial همهٔ صفحات ثابت و بازدیدهای ۴۸ ساعت اخیر گرم
  می‌شوند؛ GET/polling/گرم‌سازی، مهلت بازدید را تمدید نمی‌کنند. بازدید جدید
  دقیقاً آخرین بازدید +۴۸ ساعت است، با محافظت در برابر ترتیب معکوس درخواست‌ها.
- registry مستقل در PostgreSQL می‌ماند؛ cache payload فشرده در Redis و TTL
  مطابق زمان اجرای بعدی scheduler است. revision همچنان با دادهٔ جدید تغییر
  می‌کند. کل هفته یک پاسخ و هوا فقط از API داخلی است.
- کش عمومی CDN برای هوا ممنوع شد؛ مرورگر cache خصوصی دو دقیقه و ETag دارد.
  فایل‌های ثابت همان کش نسخه‌دار یک‌سال را حفظ می‌کنند. ظاهر، فونت و layout
  تغییری ندارند؛ منطق ورود صفحه در هر دو قالب مقصد/مسیر مشترک است.
- ۳۷ تست API/چرخهٔ کش/scheduler/استیج و ۱۸۶ تست فرانت پاس شدند. migration
  با makemigrations --check تطبیق داده شد؛ config استیج و production با nginx -t
  معتبر است. تست فشرده‌سازی، invalidation، تمدید ۴۸ساعته، انقضا، اولین مسیر و
  عدم تمدید هنگام گرم‌سازی اجرا شدند. دیپلوی انجام نشده است.

## هم‌زمانی دریافت دوره‌ای و دیپلوی استیج

دیپلوی دریافت هوا را با `--wait-lock-seconds 900` اجرا می‌کند. تنها contention
قفل ingest، هر حداکثر ۵ ثانیه و تا ۱۵ دقیقه دوباره امتحان می‌شود؛ قفل حذف
نمی‌شود و خطای provider یا دیتابیس retry/پنهان نمی‌شود. موفقیت دریافت، cache
را یک‌بار گرم می‌کند. پایان مهلت با خطای روشن، قبل از جایگزینی سرویس‌هاست.
تست‌های انتظار سپس موفقیت، timeout و عدم retry خطای provider پاس شدند.

## انتقال به main و آماده‌سازی پروداکشن

stage با main ادغام شد و مقصدهای جدید main حفظ شدند. دریافت provider برابر
۱۰ روز، Redis مشترک پیش‌فرض و نسخهٔ یکسان asset در API/SSR/web/ingest تنظیم
شدند. deploy بعد از migration/startup و sync_catalog، فرود/فاصلهٔ مشتق‌شده
را اعمال و هفته را گرم می‌کند؛ دریافت فوری هوای تازه command مجزای مستند
دارد. خاموشی کامل استیج فقط پروژهٔ hawatch-stage و volumeهای خودش را حذف
می‌کند. هیچ deploy یا حذف منابع سرور در این بررسی اجرا نشده است.

۱۸۶ تست فرانت، ۳۱ تست API/کش/انتظار ingest/دیپلوی (یک تست نیازمند Git در
image API skip شد و روی host پاس شد)، build فرانت و bash -n موفق بودند.
config واقعی Compose با env نمونه resolve شد و تطابق افق ۱۰ روز، Redis،
زمان‌بندی مشترک و نسخهٔ asset برای API/ingest/scheduler/web بررسی شد.
