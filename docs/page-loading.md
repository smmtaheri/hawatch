# بارگذاری صفحه در شبکهٔ کند

در بررسی ۱۵ اکتبر ۲۰۲۶، عقب‌انداختن پاسخ CSS مربوط به صفحهٔ پیش‌بینی در مرورگر
همان توقف «در حال آماده‌سازی صفحه…» را بازتولید کرد. در اجرای قبلی، Suspense
کل Routes را جایگزین می‌کرد و دریافت هفته بعد از آماده‌شدن کد و CSS شروع
می‌شد. این آزمایش سازوکار توقف را مشخص می‌کند؛ منشأ تأخیر واقعی کاربر در شبکه،
اپراتور یا CDN هنوز تعیین نشده است.

## قرارداد اجرا

- از اصلاح ۱۸ اکتبر، همهٔ routeهای برنامه یک JavaScript و یک CSS مشترک
  دارند؛ نمایش صفحه دیگر به دانلود lazy chunk یا stylesheet دوم وابسته نیست.
  ترتیب CSS پایه و صفحه حفظ شده است و این تغییر redesign نیست.
- Vite با `pageAssets.ts` از manifest واقعی build، `page-assets.json` می‌سازد.
  برای همهٔ صفحه‌ها همان entry با modulepreload و یک stylesheet اولیه معرفی
  می‌شوند. نام فایل‌ها در Django از artifact واقعی خوانده می‌شود.
- HTML عمومی Django و HTML مستقل صفحات وب، bootstrap کوچک یکسانی دارند.
  HTML مقصد و مسیر، payload ناشناسِ دقیقاً همان `cached_week` API داخلی را
  با `json_script` امن همراه دارد؛ renderer برای اولین نمایش GET جدا ندارد.
  دادهٔ route-week از قرارداد `week-2` استفاده می‌کند: رکوردها tupleهای دارای
  `record_fields` مشترک و تجهیزات با ارجاع per-record هستند. کلاینت فقط همین
  نسخه را می‌پذیرد؛ cache قبلی با namespaceٔ `week-11` جداست. HTML JSON فارسی را
  به UTF-8 مستقیم serialize می‌کند و escaping امنیتی `<`, `>` و `&` را حفظ
  می‌کند.
  تولید payload فقط از Redis/DB است، نه provider، حساب کاربری یا HTTP داخلی.
  Home هم JSON اولیه دارد. در HTML مستقل بدون داده، فهرست و اشتراک، bootstrap
  اولین GET لازم را آغاز و promise آن را یک‌بار به برنامه تحویل می‌دهد.
  queryهای planner، اطلاعات ورود و آمارگیری جزو این پیش‌خوانی نیستند.
- cache و single-flight هفته در `api/weekForecast.ts` مستقل از renderer/CSS
  هستند. navigation داخلی نیز آماده‌سازی داده را بیرون component آغاز
  می‌کند. خطای آماده‌سازی تا نخستین مصرف حفظ می‌شود؛ mount باعث retry پنهان
  نمی‌شود. کش سه‌صفحه‌ای، مرز نیمه‌شب و TTL پاسخ حفظ شده‌اند.
- JSON اولیه فقط با تطابق kind، slug، تاریخ تهران، هشت روز و TTL معتبر مصرف
  می‌شود. عمر HTML از TTL حافظهٔ مرورگر کم می‌شود؛ نسخهٔ منقضی یا نامعتبر
  مصرف نمی‌شود و همان GET عادی یک‌بار انجام می‌شود.
- HTML حاوی هوا در مرورگر باید revalidate شود و در CDN حداکثر ۶۰ ثانیه یا تا
  نیمه‌شب تهران (هرکدام زودتر) مجاز به کش است؛ stale-while-revalidate ندارد.
  نسخهٔ queryدار همچنان no-cache و noindex است. کش API خصوصی قبلی تغییر نکرده.
- مرز مشترک بارگذاری، Header و مقالهٔ اولیهٔ همان pathname/query را هنگام
  انتظار یا خطای chunk نگه می‌دارد. PageShell تا آماده‌شدن داده نیز همین محتوا
  را حفظ می‌کند. مقاله پس از موفقیت حذف می‌شود تا H1 یا محتوا دو بار نباشد.
- یک timer پانزده‌ثانیه‌ای فقط پیام «بارگذاری صفحه کامل نشده؛ لطفاً صفحه را
  رفرش کنید.» را نشان می‌دهد؛ خطای قطعی زودتر پیام را فعال می‌کند. پیام با
  موفقیت دیرهنگام حذف می‌شود. retry، reload خودکار یا polling برای بارگذاری
  صفحه وجود ندارد. خطای نخستین دریافت هفته با focus/visibility مجدداً امتحان
  نمی‌شود؛ چرخهٔ معمول تازه‌سازی دادهٔ سالم قبلی حفظ شده است.
- آمار داخلی و GA4 همچنان فقط navigation واقعی را ثبت می‌کنند؛ preload
  هیچ page_view یا forecast/visit نمی‌فرستد. انتخاب روز/سرعت/ساعت، عنوان و
  canonical، query/noindex و اسکرول ورود طبق قراردادهای قبلی می‌مانند.
- اولین خطا یا انتظار پانزده‌ثانیه‌ای، حداکثر یک گزارش کوچک به
  `/api/v1/diagnostics/page-load/` می‌فرستد: pathname عمومی بدون query، نسخه،
  زمان، وضعیت کد/داده و مسیر JS/CSS معطل یا ناموفق. cookie، referrer، اطلاعات
  حساب و پارامترهای planner ارسال نمی‌شوند. endpoint محدودیت اندازه/نرخ دارد،
  فقط رویداد `web.page_load_incomplete` را در لاگ موجود ثبت می‌کند و GA4،
  شمارندهٔ بازدید، DB یا retry را تغییر نمی‌دهد. دریافت گزارش هم به دسترسی
  شبکه وابسته است؛ نبود گزارش، اثبات سالم‌بودن اتصال کاربر نیست.

## انتشار و نگه‌داری فایل‌ها

Compose به‌صورت خودکار volume `hawatch_frontend_assets` را می‌سازد. web فایل‌ها
را در `/var/lib/hawatch-frontend` منتشر می‌کند و API همان volume را read-only
با `HAWATCH_FRONTEND_ASSETS_ROOT` می‌خواند؛ تنظیم دستی `.env` لازم نیست.
Stage volume جداگانهٔ خودش را دارد. تنظیم این متغیر برای اجرای API بیرون
Compose اختیاری است؛ نبود artifact فقط hints را حذف می‌کند و HTML را خراب
نمی‌کند. خطای نبود فایل cache نمی‌شود.

`publish-assets.sh` ابتدا فایل‌ها و سپس manifest را منتشر می‌کند. پنج نسخهٔ
اخیر JS/CSS و دو نسخهٔ مستقل اخیر public باقی می‌مانند؛ نسخه‌های قدیمی‌ترِ همین
پوشه‌ها حذف می‌شوند. public بدون تغییر دوباره کپی نمی‌شود. این ذخیرهٔ محدودِ
فایل‌های ثابت برای HTML کش‌شده و تب‌های باز است، نه backup دیتابیس. تب بسیار
قدیمی که به نسخه‌ای بیرون این سقف اشاره کند ممکن است به رفرش نیاز داشته باشد.
در build، CSS نهایی بعد از استخراج Vite بازنویسی می‌شود: فونت‌ها و تصویرهای
public باید به `/static-public/<public-hash>/...` اشاره کنند، نه زیرمسیر
`/static-assets/`. build اگر چنین مسیر نامعتبری ببیند یا فایل مقصد در پوشهٔ
public موجود نباشد، پیش از انتشار fail می‌شود.

در اولین انتشار این اصلاح، deploy فایل‌های نسخه‌دارِ web در حال اجرا را نیز
به volume منتقل می‌کند. سپس artifact نسخهٔ جدید و وجود تمام فایل‌های آن را
پیش از جایگزینی API بررسی می‌کند. فایل‌های قدیمی و جدید URLهای متفاوت دارند؛
فایل یک نسخه به URL نسخهٔ دیگر بازنویسی نمی‌شود. Cache-Control فایل‌های ثابت
همان یک سال immutable و سیاست API هوا همان private/no-store مشترک است.

اجرا روی سایت زنده فقط با deploy عادی اپراتور است؛ این تغییر migration ندارد.
CDN نباید headerها را override کند. فعال‌سازی CDN دوم جزو این اصلاح نیست.

اگر کاتالوگ‌های منتشرشده هنوز در Git کامل نیستند، برای hotfix کد از
`HAWATCH_SKIP_CATALOG_SYNC=1 deploy-hawatch` استفاده کنید. این گزینه فقط اجرای
`sync_catalog --apply` و `apply_route_descent` را رد می‌کند؛ اعتبارسنجی JSON و
فایل‌های build همچنان انجام می‌شود و fingerprint کاتالوگ موفق جلو نمی‌رود.
این دستور جایگزین سینک/تکمیل کاتالوگ نیست؛ deploy بعدی بدون این گزینه دوباره
سینک عادی را بررسی می‌کند. فایل‌های نیمه‌تمام کاربر نباید همراه hotfix کامیت شوند.

## اعتبارسنجی اصلاح ۱۸ اکتبر

- build/TypeScript و ۲۳۷ تست فرانت موفق؛ ۸۲ تست منتخب بکند/انتشار، شامل
  قرارداد JSON اولیه، TTL، escaping، گزارش خطا، robots و asset manifest موفق.
- ۳۴ سناریوی مرورگر با قالب واقعی Django و API کنترل‌شده: مقصد/مسیر و چهار
  صفحهٔ عمومی دیگر در عرض‌های ۳۹۰/۱۴۴۰ و تم روشن/تاریک، پیمایش و Back، تأخیر
  ۱۷٫۵ثانیه‌ای فایل اصلی و بازیابی دیرهنگام. ابعاد/تایپوگرافی با bundle زنده
  مقایسه شد؛ اختلاف اندازهٔ متن زیر دو پیکسل بود. H1 یکتا، نبود overflow، یک
  pageview و یک visit، گزارش منفرد و حذف پیام پس از موفقیت بررسی شدند.
- اولین نمایش مقصد و مسیر با پاسخ 503 عمدی endpoint هفته همچنان کامل بود:
  HTML معتبر JSON دارد و درخواست جداگانه‌ای برای هفته نمی‌فرستد. این آزمون
  به معنی تحمل قطعی فایل اصلی JavaScript یا کل شبکه نیست.
- فایل‌های ضروری از دو JS و دو CSS به یک JS و یک CSS کاهش یافتند. خروجی
  فشردهٔ build جدید حدود ۱۱۴٫۶KB JS و ۲۰٫۸KB CSS است؛ HTML اکنون JSON عمومی
  هفته را هم حمل می‌کند. این اعداد اندازهٔ artifact هستند، نه سرعت اپراتور.
- در اجرای اولیهٔ گسترده‌تر DB، دو تست فرود شهرستانک و تکرار
  `apply_route_descent` شکست خوردند. در آماده‌سازی دیپلوی کامل، انتظار قدیمیِ
  تست با fixture بازبینی‌شدهٔ ۳۲ متر هماهنگ شد و مقایسهٔ evidence نهایی اصلاح
  شد تا اجرای بی‌تغییر، write و invalidation اضافی نداشته باشد. هر ۱۹ تست هفته،
  شامل زنجیرهٔ نامطابق، حفظ فاصلهٔ curated و dry-run بدون write، موفق شدند.
  این بررسی منتخب است، نه ادعای اجرای کل suite بکند.

## آمادگی کاتالوگ برای دیپلوی کامل، ۱۸ اکتبر

چهار fixture باقی‌ماندهٔ قشم/هرمزگان، طبیعت شمال، متین‌آباد و شوی نسخه‌دار شدند.
۱۳ WeatherPoint آن‌ها از قبل در production فعال و دارای forecast بودند؛ gate
Open-Meteo/DEM هر ۱۳ مورد دوباره پاس شد. مقایسهٔ کامل prospective با دیتابیس
زنده در transaction فقط‌خواندنی، برای ۲۵۱ fixture، ۱۱۰۳ نقطه و ۲۴۶ مسیر،
هیچ create/update، حذف/غیرفعال‌سازی یا conflict گزارش نکرد. این بررسی خودش
import، ingest، pull سرور یا deploy انجام نداده است.

در آزمایش دیتابیس تازه، بازنویسی بی‌دلیل درصد پیشروی RoutePoint نیز پیدا شد:
مقدار ذخیره‌شدهٔ Decimal با float مقایسه می‌شد. importer و normalizer اکنون
همان فرمول و همان گردکردن قبلی را با نوع Decimal مشترک مقایسه می‌کنند؛ عددهای
عمومی، هندسه و ETA تغییر نکرده‌اند. اجرای بی‌تغییر نباید timestamp مسیر یا
revision کش هوا را تغییر دهد.

اجرای نهایی ۴۹ تست منتخبِ اعتبارسنجی، bootstrap دیتابیس تازه، preflight، سینک
کامل و تکرار آن، انتشار مسیر، هفته و اسکریپت دیپلوی موفق بود. تست قدیمیِ انتشار
ادمین نیز با مدل فعلی pace/ارتفاع هماهنگ شد؛ منطق ETA محصول تغییر نکرده است.

گنو قبلاً منتشر نشده بود؛ gate آن به‌دلیل فاصلهٔ ۵٫۸۶۳ کیلومتری سلول در برابر
سقف ۵٫۲۵ کیلومتر رد شد. فایل به `docs/drafts/catalog/geno_peak_v1.json` منتقل
و در Git حفظ شد، اما جزو fixtureهای production نیست. دادهٔ نامعتبر برای تمیزکردن
worktree فعال یا حذف نشد. اکنون دیپلوی کامل عادی با `deploy-hawatch` نیاز به
گزینهٔ موقت ردکردن sync ندارد. بعد از deploy، کش HTML در CDN پاک و همان URLها
با ایرانسل و رایتل بررسی شوند؛ نتیجهٔ آزمایش محلی تضمین سلامت همهٔ مسیرهای شبکه نیست.

## اعتبارسنجی قبلی، ۱۵ اکتبر

- build و TypeScript موفق؛ ۲۲۴ تست فرانت، شامل GA4، آمار داخلی، اسکرول ورود،
  queryها، اشتراک و استفادهٔ مشترک از درخواست اولیه موفق شدند.
- ۱۷ بررسی منتخب Python برای HTML، manifest، انتشار/retention فایل‌ها و روند
  deployment موفق شدند؛ نیازی به DB یا فراخوانی provider نداشتند.
- ۳۶ سناریوی Chromium با HTML قالب واقعی Django و API کنترل‌شده اجرا شد:
  شش صفحه در عرض‌های ۳۹۰/۱۴۴۰ و تم روشن/تاریک، پیمایش مقصد → مسیر و Back،
  تأخیر CSS، قطع chunk، خطای API، انتظار بیش از پانزده ثانیه برای API یا
  فایل اصلی و بازیابی با رفرش دستی. عنوان، H1 یکتا، حفظ محتوای اولیه، نبود
  overflow و عدم درخواست تکراری بررسی شدند. گوگل در این محیط مسدود بود؛
  این بررسی تأیید دریافت واقعی داده در GA4 نیست.
- با تأخیر عمدی پنج‌ثانیه‌ای CSS، شروع GET هوا در نسخهٔ قبلی ۵۲۷۹/۵۲۴۹ms
  و در نسخهٔ جدید ۱۱۶/۱۲۶ms بود (به‌ترتیب موبایل/دسکتاپ). این عدد زمان آغاز
  درخواست در آزمایش محلی است، نه زمان تکمیل صفحه یا سرعت production.
- فایل‌های ضروری مقصد/مسیر از شش درخواست ثابت (چهار JS و دو CSS) به چهار
  درخواست (دو JS و دو CSS) کاهش یافتند. فایل اصلی فشرده از ۸۹۸۸۶ به حدود
  ۹۱۰۰۰ بایت رسید؛ فایل CSS اصلی حدود ۷۷ بایت افزایش داشت. HTML نیز bootstrap
  کوچک inline دارد. برای صفحات دیگر کد پیش‌بینی دانلود نمی‌شود.
- پیکربندی Nginx اصلی و QA با `nginx -t` بررسی شد؛ GET واقعی فایل نسخه‌دار،
  فایل گمشده، صفحهٔ اشتراک و ممنوعیت دسترسی مستقیم به HTML داخلی بررسی شد.

تصاویر وضعیت انتظار با دادهٔ کنترل‌شده در `design/screens/page-loading/` هستند.
سرعت واقعی شبکه‌های همراه و CDN پس از انتشار باید جداگانه اندازه‌گیری شود.
آزمایش کندکردن پاسخ در مرورگر تنها بازتولید سازوکار است، نه اثبات اشکال یک
اپراتور یا CDN مشخص. تغییر DNS اصلی پیش از مقایسه با ایرانسل/رایتل توصیه نمی‌شود.
