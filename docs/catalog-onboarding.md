# راهنمای استاندارد افزودن نقطه و مسیر

این سند مرجع اصلی افزودن نقاطی جدید به هواچ است. برای شروع کار نفر بعدی
همین سند را کامل بخواند؛ قرارداد جزئی‌تر فیلدها در
[`catalog-and-weather-validation.md`](catalog-and-weather-validation.md) و رفتار
forecast در [`api/forecast-contract.md`](api/forecast-contract.md) است.

## اصل معماری

دیتابیس منبع حقیقت runtime است. نقطه، WeatherPoint، Route و RoutePoint بعد از
import در دیتابیس ذخیره می‌شوند و برای اضافه‌کردن آن‌ها deploy یا migration لازم
نیست.

قبل از تحویل کار، fixture منتشرشده را همراه تغییرات مرتبط commit/push کنید؛
انتشار دیتابیس به‌تنهایی کافی نیست، چون sync کاملِ release فقط fixtureهای
نسخه‌دار را می‌بیند و ممکن است دادهٔ fixture-managed غایب را stale تشخیص دهد.
پیش‌نویسِ منتشرنشده که gate آن رد شده باید بیرون از
`apps/api/fixtures/catalog/`، مثلاً در `docs/drafts/catalog/`، نگه‌داری و دلیل
توقفش ثبت شود؛ صرفِ کامیت یا تمیزکردن worktree مجوز فعال‌کردن آن نیست.

فایل JSON فقط یک ورودی versioned برای import است. می‌تواند در `/tmp` یا یک
مخزن خصوصی نگه‌داری شود و با `--stdin` از کامپیوتر اپراتور به کانتینر API
فرستاده شود؛ فایل JSON و GPX لازم نیست روی سرور کپی شوند.

کدهای عمومی این workflow در repository هستند:

- `scripts/validate_open_meteo_catalog.py`: اعتبارسنجی read-only مختصات، DEM و provider؛
- `scripts/analyze_route_tracks.py`: تحلیل read-only GPX روی کامپیوتر محلی؛
- `scripts/publish_catalog.py`: اجرای استاندارد کل workflow محلی/SSH؛
- `seed_catalog --stdin`: check-only یا import اتمیک در دیتابیس؛
- `ingest_open_meteo`: ذخیرهٔ forecast نقاط فعال؛
- `catalog_preflight`: بررسی read-only دادهٔ واقعی داخل دیتابیس.

## روال سریع پیش‌فرض برای افزودن نقطه

برای یک افزودن معمولی و افزایشی، این روال کافی است؛ کارهای release یا audit
کامل را به این مسیر اضافه نکنید:

1. هویت، نام/slug، منبع مختصات و ارتفاع را بررسی کنید. نام و شکل‌های رایج آن را
   در fixtureها و دیتابیس جست‌وجو کنید و یک lookup مکانی فقط‌خواندنی برای
   نزدیک‌ترین WeatherPointهای فعال انجام دهید. لازم نیست برای هر نقطه، validator
   سراسریِ زوج‌به‌زوج کل دیتابیس را اجرا کنید.
2. بررسی مسیر پیاده بخشی از صورت‌مسئلهٔ **هر مقصد جدید** است؛ حتی اگر احتمال
   می‌دهید در نهایت point-only باشد. پیش از تصمیم نهایی، مسیرهای شناخته‌شدهٔ
   همان مقصد را در وب و کاتالوگ هواچ جست‌وجو کنید، مبدأ/مقصد و سختی احتمالی را
   مشخص کنید و نتیجهٔ بررسی را ثبت کنید. معیارهای پذیرش در بخش «دروازهٔ انتخاب
   مسیر: شواهد مستقل، شناخته‌شدن و ماهیت پیمایش» آمده است.
3. اگر مقصد با خودروی عادی تا خودِ نقطهٔ نماینده قابل‌دسترسی است و مقصد کوه/قله
   نیست، در صورت پیدا نشدن Route واجد شرایط می‌توان یک WeatherPoint مستقل با
   `routes: {}` ساخت. اما هر کوه/قله و هر مقصدی که خودرو تا خودِ مقصدش نمی‌رسد
   باید پیش از انتشار دست‌کم یک Route پیادهٔ واجد شرایط با ترک GPX بررسی‌شده
   داشته باشد؛ اگر چنین ترکی پیدا نشد، آن مقصد را point-only منتشر نکنید و
   onboarding/انتشارش را متوقف کنید. برای point-onlyهای مجاز، GPX، دانلود ترک،
   فولدر `tracks/`، تحلیل Route یا بررسی timing لازم نیست. اگر چند نقطهٔ یک
   خوشه را با هم اضافه می‌کنید، آن‌ها را در یک catalog بیاورید تا validation
   و import یک‌بار برای کل batch انجام شود.
4. catalog را با `validate_catalog --file <catalog> --strict` بررسی کنید. هنگام
   اجرای `scripts/publish_catalog.py --apply`، gate اجباری Open-Meteo/DEM، بررسی
   شکل ورودی روی سرور، import اتمیک، ingest هدفمند و `catalog_preflight` همان نقطه
   در همان اجرا انجام می‌شوند.
5. wrapper را مستقیم یک‌بار با `--apply` اجرا کنید؛ ابتدا اجرای check-only و سپس
   اجرای مجدد با `--apply` نکنید، چون بررسی شبکه‌ای Open-Meteo دوباره اجرا می‌شود.
   برای تشخیص خطا می‌توان validator مستقل را جداگانه اجرا کرد، اما آن را بی‌دلیل
   پیش از wrapper تکرار نکنید.

```bash
python3 scripts/publish_catalog.py \
  --catalog apps/api/fixtures/catalog/<catalog>_v1.json \
  --host hawatch \
  --point <primary-point-slug> \
  --apply
```

این مسیر **بک‌آپ دیتابیس نمی‌گیرد، migration/restart نمی‌کند و کل catalogها را
sync نمی‌کند**. Import افزایشی اتمیک و بدون `--prune` است. بک‌آپ را فقط برای
عملیات تخریبی/گسترده، migration یا تغییر دادهٔ پرریسک، یا با درخواست صریح
اپراتور بگیرید. `sync_catalog --dry-run/--apply` و validatorهای `--all` برای
sync عمدی کل fixtureها، اصلاح گسترده یا audit دوره‌ای‌اند؛ اجرای آن‌ها برای هر
نقطهٔ جدید لازم نیست.

بررسی نام و مختصات در کل داده همچنان لازم است، اما باید هدفمند باشد: fixtureها
را برای slug/name/alias جست‌وجو کنید و در دیتابیس فقط نزدیک‌ترین نقاط به مختصات
candidate را بخوانید. نمونهٔ PostGIS زیر فاصلهٔ دقیق را برحسب متر می‌دهد؛ نام
کاربر و دیتابیس از env همان container خوانده می‌شود:

```bash
docker compose --env-file .env -f infra/compose/compose.yaml exec -T postgres sh -lc \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "
    SELECT slug, name,
           round(ST_DistanceSphere(location, ST_SetSRID(ST_MakePoint(<longitude>, <latitude>), 4326)))::int AS distance_m
    FROM forecasts_weatherpoint
    WHERE is_active
    ORDER BY ST_DistanceSphere(location, ST_SetSRID(ST_MakePoint(<longitude>, <latitude>), 4326))
    LIMIT 10;"'
```

فاصلهٔ کمتر از ۲۵ متر را duplicate فرض کنید؛ فاصلهٔ ۲۵ تا ۱۰۰ متر نیازمند
بازبینیِ استقلال دو عارضه و ثبت دلیل است. اگر نقطهٔ نزدیک همان مکان canonical
است، رکورد موجود را reuse کنید. جزئیات قرارداد نام، مسیر و دادهٔ جغرافیایی در
بخش‌های بعد و سند [`catalog-contribution.md`](catalog-contribution.md) آمده است.

## داده‌های لازم

### نقطه

برای هر نقطه یک رکورد با این اطلاعات لازم است:

- `slug` یکتا و پایدار، مثلاً `damavand`؛
- نام، نام کوتاه، منطقه و `category_key`؛ برای دماوند `volcano`؛
- مختصات canonical به‌صورت WGS84 ده‌دهی؛
- ارتفاع معتبر و منبع آن؛
- `climate`، تصویر و alt text؛
- نقطه جدید به‌صورت پیش‌فرض محبوب نیست. مجموعهٔ حداکثر چهار نقطه محبوب هوم را با
  command مدیریتی `set_popular_points` و به‌ترتیب دلخواه تنظیم کنید؛ لازم
  نیست برای تغییر آن کد یا migration بسازید. انتخاب محبوب یک تنظیم اپراتوری
  است و `sync_catalog` در deployهای بعدی آن را بازنشانی نمی‌کند.

برای SEO، title/description/content را فقط در صورت داشتن copy مستند در بلوک
اختیاری `seo` همان row بنویسید. در غیر این صورت renderer نام، نوع عارضه، ارتفاع،
منطقه و forecast واقعی را خودکار به copy یکتا تبدیل می‌کند. همهٔ ردیف‌های فعال
در فهرست و مسیرهای اپ باقی می‌مانند؛ فقط ردیف‌های `seo_indexable=false` از
sitemap خارج و صفحهٔ مستقلشان با وجود ۲۰۰ بودن `noindex,follow` می‌شود. جزئیات
در [`seo.md`](seo.md) است.

### مقصدهای مهم و فهرست مقصدها

هر نقطهٔ مستقل، شناخته‌شده و قابل جست‌وجو که برای کاربر یک مقصد واقعی است (مثل
قله، دریاچه، آبشار، دشت یا روستای شناخته‌شده) باید در catalog با
`kind: "primary"`، `importance: "primary"` و `seo_indexable: true` ثبت شود.
این سه مقدار منبع حقیقت عضویت خودکار نقطه در Hub مقصدهای `/destinations` هستند؛
برای اضافه‌کردن مقصد جدید هیچ فهرست hardcode یا تغییر جداگانه‌ای در frontend
لازم نیست. نقطه‌های فنی، بین‌راهی، مبدأهای صرفاً دسترسی و landmarkهای پشتیبان
باید `kind`/`importance` متناسب و معمولاً `seo_indexable: false` داشته باشند تا
در مسیر، جست‌وجو و API باقی بمانند اما مقصد مستقل و ورودی sitemap نشوند.

پیش از import بررسی کنید نقطه واقعاً مقصد مستقل است، نام و مختصات آن با همهٔ
catalogها و WeatherPointهای فعال duplicate نیست و نوع عارضه درست ثبت شده است.
پس از `sync_catalog --apply`، Hub، sitemap و لینک‌های SSR آن را خودکار می‌بینند؛
این قاعده برای همهٔ نقاط آینده نیز لازم‌الاجراست.

برای هر کوه/قله و هر مقصدی که خودرو تا خودِ نقطهٔ مقصد به آن نمی‌رسد، Route پیاده
و ترک GPX معتبر شرط انتشار صفحهٔ مقصد است؛ این شرط با رسیدن خودرو به پارکینگ یا
پای مسیر برآورده نمی‌شود. مسیر باید از مبدأ واقعی تا مقصد پیوسته باشد، حداقل یک
عارضهٔ میانی واقعی و مستند داشته باشد و از دروازهٔ شواهد مستقل، شناخته‌شدن و
قابل‌عبوربودن عبور کند. سختی زیاد، شیب تند یا دست‌به‌سنگِ معمول به‌تنهایی دلیل
رد مسیر نیست؛ مسیر اصلیِ شناخته‌شده را حتی اگر دشوار باشد بررسی و با سختی و
هشدارهای مستندش معرفی کنید. اگر چنین ترکی پیدا یا
تأیید نشد، نه Route ساختگی بسازید و نه مقصد را point-only منتشر کنید؛ انتشار آن
مقصد تا تکمیل شواهد متوقف می‌ماند. `routes: {}` فقط برای point-onlyهای مجاز، از
جمله مقصدهایی که خودرو تا نقطهٔ نماینده‌شان می‌رسد و کوه/قله نیستند، استفاده
می‌شود. وضعیت `pending` برای Route ناقص یا فاقد شواهد است و جای Route اجباری
برای کوه/مقصد پیاده‌دسترس را نمی‌گیرد. هرگز ترک خودرو، آفرود، دوچرخه یا مسیر
صخره‌نوردیِ فنیِ ابزار/طناب‌محور را به‌جای Route پیاده ثبت نکنید؛ دشواربودن یا
دست‌به‌سنگِ معمول مانع نیست.

`category_key` فقط متن دسته‌بندی نیست؛ کلید معنایی آیکون نقطه هم هست و از
دیتابیس به فرانت می‌رسد. برای مثال، اسکلیم باید `waterfall` داشته باشد و قله‌های
آتشفشانی مانند دماوند و تفتان باید `volcano` داشته باشند؛ صرف summit بودن به‌تنهایی
به معنی کوه معمولی نیست. بعد از اضافه‌شدن یک کلید به مجموعهٔ runtime، ثبت نقاطی بعدی با یکی
از کلیدهای موجود فقط با import کاتالوگ یا Admin انجام می‌شود و deploy جداگانه
لازم ندارد. برای ارتفاعات و خط‌الرأس، `ridge` استفاده شود؛ این کلید در UI با
خانوادهٔ `mountain` نمایش داده می‌شود. برای ساحل نیز `beach` و برای دشت، کویر
و آبشار به‌ترتیب `meadow`، `desert` و `waterfall` ثبت شوند. برای خودِ دره، نوع
معنایی `place_type: "valley"` و کلید `category_key: "valley"` به‌کار رود؛ نوع
مقصد باید ماهیت واقعی مکان را بیان کند، نه اینکه فقط برای گرفتن یک آیکون انتخاب
شود. برای محله‌های شهری
مثل ولنجک از `place_type: "neighborhood"` و `category_key: "neighborhood"` استفاده
کنید؛ محله با `village` یکی نیست. شهرها با `place_type: "city"` و
`category_key: "city"` ثبت می‌شوند و آیکون بافت شهری مستقل دارند؛ محله و شهر
نباید یک کلید بصری مشترک داشته باشند. کلید ناشناخته نباید
استفاده شود؛ UI برای جلوگیری از نمایش گمراه‌کننده به‌جای کوه، نشان خنثی نشان
می‌دهد.

در طراحی فعلی، دسته‌های اختصاصی `cave` (غار)، `ski` (پیست)، `marsh`
(مرداب)، `fort` (قلعه)، `dam` (سد)، `hot_spring` (آبگرم)، `bridge` (پل)،
`rocks` (عارضهٔ سنگی)، `park` (پارک)، `gorge` (تنگه)، `valley` (دره)،
`terrace` (چشمهٔ پلکانی) و `kalut` (کلوت) نیز آیکون بستهٔ ریدیزاین دارند.
آن‌ها را در `weather_points.<slug>.category_key` و، برای نقطهٔ شاخص، در
`point.category_key` یکسان ثبت کنید؛ برای این کار نوع معنایی `place_type`
را صرفاً به‌خاطر آیکون تغییر ندهید. نوع عمومی `landmark` نباید دستهٔ اختصاصی
را بپوشاند. resolver مشترک فرانت، دستهٔ اختصاصی را انتخاب می‌کند؛ خانوادهٔ
عمومی `mountain`/`ridge` همچنان آیکون مشخص پناهگاه، گردنه و مبدأ را نمی‌پوشاند.
تغییر این متادیتا به migration یا ingest دوباره نیاز ندارد، اما fixture جدید
باید هنگام انتشار با دیتابیس همگام شود. دستهٔ معنایی در لینک‌های «مقصدهای
مشابه» هم استفاده می‌شود، بنابراین این لینک‌ها پس از تغییر دسته بررسی شوند.

هر نقطه باید فقط یک بار در `weather_points` تعریف شود. نقطهٔ شاخص با
`kind: "primary"` مشخص می‌شود و صفحهٔ آن نیز همان `/points/{slug}` است؛ سایر
نقاط مسیر با `kind: "shared"` یا `kind: "route_point"` ثبت می‌شوند.

### نقطهٔ بدون مسیر (point-only)

`point-only` فقط برای مقصدی مجاز است که خودِ نقطهٔ نماینده‌اش با خودروی عادی و
از راه دسترسی غیرآفرودی قابل‌رسیدن باشد و ماهیت مقصد کوه/قله یا هدف صعود/پیمایش
پیاده نباشد؛ مانند بعضی دریاچه‌ها، روستاها، محوطه‌های تاریخی یا جاذبه‌هایی که
جاده تا خود مقصد دارند. دسترسی خودرو تا پارکینگ/پای مسیر به معنی دسترسی خودرو تا
خود مقصد نیست. هر کوه/قله و هر مقصدی که دسترسی نهایی‌اش پیاده است، پیش از انتشار
باید Route و ترک GPX واجد همهٔ معیارهای کیفیت این سند داشته باشد. اگر مسیر
معتبر پیدا نشد یا ترک موجود صخره‌نوردیِ فنی/نامستند بود، مقصد را point-only منتشر نکنید
و تا تکمیل شواهد در catalog زنده وارد نکنید. ترک خودرو یا آفرود هرگز Route پیاده
محسوب نمی‌شود.

برای point-only مجاز:

- یک canonical point WeatherPoint با مختصات و ارتفاع معتبر کافی است؛
- `routes` باید یک آبجکت خالی (`{}`) باشد، نه اینکه حذف شود؛
- GPX لازم نیست و timing، distance و ascent مسیر نداریم؛
- forecast همان نقطه با ingest عادی ذخیره می‌شود و `catalog_preflight` فقط
  profile/provider را بررسی می‌کند؛
- UI نقطه بدون route را با وضعیت «هنوز مسیری برای این نقطه ثبت نشده» نشان می‌دهد.

این بخش معافیت فنی GPX برای forecast را بیان می‌کند، نه اجازهٔ point-only برای
کوه‌ها/قله‌ها یا مقصدهای فقط‌پیاده‌دسترس. برای آن‌ها route gate پیش‌نیاز انتشار
است.

### اولویت‌بندی فصلی مقصدها

در برنامه‌ریزی انتشار می‌توان مقصدهای شناخته‌شده‌ای را که در فصل جاری ارزش
طبیعت‌گردی یا پایش آب‌وهوا دارند (برای نمونه قله‌های جنگلی در پاییز) در اولویت
گذاشت. این اولویت فقط ترتیب بررسی است و نباید باعث حدس‌زدن نام، مختصات، ارتفاع
یا شرایط فصلی شود. برای هر مقصد، ابتدا هویت و دادهٔ آب‌وهوا را با منبع واقعی
تأیید کنید؛ سپس با توجه به دسترسی تصمیم بگیرید: برای مقصد قابل‌دسترسی با خودرو
که کوه/قله نیست، point-only ممکن است؛ برای هر کوه/قله یا مقصد فقط‌پیاده‌دسترس،
ابتدا Route و ترک واجد شرایط را پیدا و تأیید کنید و تا آن زمان منتشر نکنید.

نمونهٔ فعلی: دریاچهٔ تار با مختصات نمایندهٔ پهنهٔ آبی
`35.730520, 52.227850` و elevation کاتالوگ `2896 m` ثبت شده است. Open-Meteo
برای همین نقطه DEM برابر `2896 m` و نزدیک‌ترین grid در فاصلهٔ حدود `2.95 km`
برگرداند؛ این برای forecast قابل‌قبول است اما دقت پیش‌بینی واقعی را تضمین
نمی‌کند. منابع بررسی دسترسی و موقعیت: [OSM/Mapcarta](https://mapcarta.com/13159408)،
[Wikipedia](https://en.wikipedia.org/wiki/Lake_Tar)، و
[راهنمای دسترسی](https://zooomlite.ir/%D8%AF%D8%B1%DB%8C%D8%A7%DA%86%D9%87-%D8%AA%D8%A7%D8%B1-%D8%AF%D9%85%D8%A7%D9%88%D9%86%D8%AF/).

### WeatherPoint

برای هر نقطه:

- slug یکتا، نام و مختصات دقیق؛
- `elevation_m` از منبع قابل‌اعتماد، ترجیحاً DEM/PBF تأییدشده؛
- `elevation_source` یا `evidence_note` برای audit؛

قبل از افزودن نقطه، مالک catalog را مشخص کنید. هر slug فقط یک‌بار در کل fixtureها
تعریف می‌شود؛ نقطهٔ مشترک در catalogهای دیگر فقط با `shared_weather_points`
ارجاع می‌گیرد. برای تغییر catalog موجود، فایل فعال را version بعدی کنید و فایل
version قبلی را در پوشهٔ package نگه ندارید، چون loader مالکیت تکراری را رد می‌کند.
نقطهٔ جدید در Home محبوب نمی‌شود مگر آن‌که صریحاً با `set_popular_points` انتخاب
شود. `seo_indexable` فقط discoverability را مشخص می‌کند: برای نقطهٔ مستقلِ قابل
جست‌وجو `true` و برای waypoint فنی/بین‌راهی `false` بگذارید. مقدار false رکورد را
غیرفعال نمی‌کند و آن نقطه همچنان در route، search، API و forecast باقی می‌ماند؛
فقط صفحهٔ مستقل noindex و خارج از sitemap می‌شود. اگر point type فنی بدون این
فیلد باشد، policy مرکزی به‌صورت پیش‌فرض noindex اعمال می‌کند.

### قواعد نام‌گذاری نقطه‌ها

- پیش از انتخاب نام و slug هر نقطه، کنترل اجباری «کوتاه‌ترین هویت معنادار و
  یکتا» را در [قرارداد مشارکت](catalog-contribution.md#کوتاه‌ترین-هویت-معنادار-و-یکتا)
  انجام دهید: هم کل catalog و دیتابیس، هم منابع بیرونیِ مقصدهای طبیعت‌گردی و
  سکونتگاه‌ها بررسی شوند. آزادبودن slug در پروژه به‌تنهایی کافی نیست.
- پسوندهایی مثل `peak`، `village` و نام استان/قلهٔ مادر فقط برای رفع ابهام واقعی
  اضافه شوند، نه به‌صورت پیش‌فرض. نام نمایشی باید کوتاه، رایج و قابل‌شناسایی
  باشد؛ کوتاه‌کردن URL نباید نام مکان را مبهم یا مخفف ساختگی کند.
- `WeatherPoint.name` باید نام یک عارضهٔ واقعی و قابل‌شناسایی باشد؛ نام‌های
  عمومی مثل «محل استراحت مسیر»، «شیب نهایی قله» یا «کمپ سوم» بدون ذکر
  مسیر/مکان قابل قبول نیستند.
- اگر یک نقطه بین چند مسیر مشترک است، نام canonical آن باید مستقل از یک
  مسیر خاص و همچنان قابل‌شناسایی باشد؛ برای متن route-specific از
  `RoutePoint.name` استفاده کنید، چون همین مقدار در تایم‌لاین عمومی نمایش داده
  می‌شود.
- نقطهٔ میانی باید یک عارضهٔ واقعی مثل گردنه، پناهگاه، چشمه، تقاطع مشخص،
  دریاچه یا چشم‌انداز مستند باشد. صرفاً «استراحتگاه» یا «توقفگاه میانی» نقطهٔ
  قابل انتشار نیست؛ اگر نام واقعی پیدا نشد، آن نقطه را به زنجیرهٔ عمومی اضافه
  نکنید.
- نام‌های ارتفاعی باید کوه/یال و ارتفاع را کامل داشته باشند؛ مثلاً
  «یال غربی دماوند · ارتفاع ۵۰۰۸ متر».
- برای عارضه‌های شماره‌دار، نام مکان را همراه شماره بیاورید؛ مثلاً «ایستگاه ۱
  توچال»، نه «ایستگاه ۱». برای پناهگاه‌ها و جان‌پناه‌ها نیز نوع عارضه را در
  نام بیاورید؛ مثلاً «جان‌پناه امیری»، نه «امیری».
- `name` باید برچسب نمایشی یکتا و روشن باشد و `aliases` شکل‌های کوتاه، فاصله‌دار
  یا رایج همان نام را پوشش دهد تا جست‌وجو حفظ شود. اگر هویت نقطه تغییر کرد، slug
  canonical را در همهٔ fixtureها، API، frontend و مستندات یک‌جا عوض کنید؛ URL قدیمی
  عمداً redirect یا نگاشت legacy ندارد.
- نام‌های کوتاه و پرت که بدون زمینه با چند نقطه قاطی می‌شوند یا در جست‌وجوی گوگل
  قابل تشخیص نیستند، مجوز افزودن ندارند. زمینهٔ جغرافیایی/مسیر را در نام بیاورید:
  «تپهٔ گوگردی دماوند» قابل قبول است، اما «تپهٔ گوگردی» نه؛ «استراحتگاه مسیر
  شمالی علم‌کوه» قابل قبول است، اما «استراحتگاه» نه. اگر نام یکتا و قابل جست‌وجو
  پیدا نشد، نقطه را فعلاً به catalog اضافه نکنید.
- اگر ارتفاع هنوز قطعی نیست، مقدار `null` و وضعیت provisional استفاده شود؛
- GPX `<ele>` به‌تنهایی حقیقت ارتفاع نیست.

### ادغام مبدأهای نزدیک روستا

هر ترک جدید باید پیش از ساخت catalog با تمام نقاط فعال و fixtureهای موجود
مقایسه شود. اگر waypoint شروع، مسجد، پارکینگ یا محل سوارشدن در محدودهٔ همان
روستا و در عمل همان مبدأ جغرافیایی است، نقطهٔ canonical را خودِ روستا قرار
دهید و عارضهٔ شروع را WeatherPoint جدا نسازید. این ادغام نام روستا و مسیر را
حفظ می‌کند و از دو صفحهٔ تکراری برای یک مکان جلوگیری می‌کند.

«نزدیک» فقط یک شعاع عددی نیست: نام عارضه در منبع، پیوستگی با بافت روستا و
مختصات چند ترک را هم بررسی کنید. اگر محل شروع بیرون از روستا و یک access point
مستقل و نام‌دار است (برای نمونه پارکینگ یا پاسگاه چند کیلومتر دورتر)، آن را
فقط در صورت ارزش مستقل برای کاربر ثبت کنید؛ معمولاً نوع فنی آن
`seo_indexable: false` خواهد بود و همچنان داخل مسیر می‌ماند. برای فاصلهٔ کمتر از ۲۵ متر همیشه
merge لازم است؛ فاصلهٔ ۲۵ تا ۱۰۰ متر فقط با عارضهٔ مستقل، نام روشن و ثبت علت در
`reviewed_nearby_point_pairs` مجاز است. این قاعده برای همهٔ نقاط و مسیرهای
آینده است، نه فقط یک قله یا یک catalog.

GPX برای گرفتن آب‌وهوا لازم نیست. مختصات و ارتفاع برای ساخت WeatherPoint
کافی است؛ GPX فقط برای بررسی هندسه، فاصله، صعود و نقاط میانی مسیر استفاده می‌شود.

### حداقل کیفیت route و انتخاب ترک

این بخش برای هر Route gate اجباری قبل از ساخت catalog است. هر فایلی
که فقط به گهر، دماوند یا هر نقطه دیگری نزدیک باشد، خودبه‌خود evidence معتبر route
نیست. بررسی مسیر برای هر مقصد جدید الزامی است؛ point-only مجاز به GPX نیاز ندارد،
اما برای هر کوه/قله و مقصدی که خودرو به خودِ آن نمی‌رسد، یافتن و تحلیل GPX
پیش‌شرط انتشار است.

#### دروازهٔ انتخاب مسیر: شواهد مستقل، شناخته‌شدن و ماهیت پیمایش

Route عمومی هواچ باید مسیر واقعی و شناخته‌شدهٔ پیاده‌روی/کوه‌پیمایی باشد، نه صرفاً
ثبت هر ترک پیدا‌شده. مسیر اصلی و معمولِ صعود را در اولویت بگذارید. پیش از انتخاب
ترک یا درخواست دانلود، همهٔ شرط‌های زیر را برای **همان مسیر مشخص** بررسی کنید:

- **تأیید مستقل در وب:** علاوه بر صفحهٔ ترک/ردّ GPX، دست‌کم یک منبع عمومیِ
  مستقل و خارج از Wikiloc باید خودِ همین مسیر پیاده را توصیف یا تأیید کند؛ مثلاً
  راهنمای محلی معتبر، باشگاه/راهنمای کوه‌پیمایی، مرجع گردشگری یا گزارش روشن
  پیمایش. صفحه‌ای که فقط خود مقصد را معرفی می‌کند، مسیر دیگری را می‌گوید یا
  متن Wikiloc را بازنشر کرده، تأیید مستقل محسوب نمی‌شود. اگر ترک از منبعی غیر
  از Wikiloc است نیز یک منبع مستقلِ دیگر برای تأیید همان مسیر لازم است.
- **شناخته‌شده و واقعاً مورد استفاده:** شواهد باید نشان دهند مسیر مشخص و رایج
  است، نه ترک مبهم و کم‌اعتبار. تعداد بازدید/دانلود/لایک ترک، اگر موجود باشد،
  فقط یک قرینه است و معیار یگانه نیست؛ منبع مستقل هم باید همان مسیر را به‌عنوان
  مسیر شناخته‌شده/معمول معرفی کند یا گزارش پیمایش روشن آن را داشته باشد. ترک
  کم‌تعامل که بیرون از Wikiloc شواهدی از شناخته‌شدن و استفادهٔ واقعی ندارد وارد
  catalog نشود. عدد حداقلیِ ثابت برای لایک جعل نکنید.
- **پیاده، پیوسته و قابل‌عبور:** منبع‌ها باید کاربری پیاده و قابل‌دنبال‌کردن
  مسیر را پشتیبانی کنند و ترک، همان مبدأ، landmark میانی و مقصد را پیوسته
  پوشش دهد. صرف وجود geometry در GPX، عنوان Wikiloc یا قابل‌تحلیل‌بودن فایل
  عبورپذیری مسیر را ثابت نمی‌کند. دسترسی/بسته‌بودن مسیر و موانع شناخته‌شده را
  نیز در منابع بررسی کنید.
- **سختی، شیب و دست‌به‌سنگ:** برچسب‌هایی مثل سخت/خیلی سخت، شیب تند، دست‌به‌سنگ
  یا مناسب‌بودن برای کوهنورد باتجربه به‌تنهایی دلیل رد Route نیست و شرط آسان‌بودن
  برای مبتدی نداریم. این ویژگی‌ها را از گزارش‌ها و شواهد مسیر ثبت کنید تا سختی
  واقعی پنهان یا مسیر اصلی حذف نشود. اگر چند مسیر وجود دارد، مسیر اصلی و جاافتاده
  را مقدم کنید؛ مسیر فرعی را فقط وقتی کنار بگذارید که مسیر اصلیِ بهتر و مستندتری
  وجود داشته باشد.
- **مرز مسیر فنی:** مسیر صخره‌نوردی/سنگ‌نوردیِ واقعی را به‌عنوان hiking Route ثبت
  نکنید؛ منظور مسیری است که ماهیت آن صعود فنی با ابزار، طناب/حمایت یا مهارت
  صخره‌نوردی است. این ممنوعیت شامل دست‌به‌سنگِ معمول، scrambling، شیب تند یا
  دشواری کلی کوه‌پیمایی نیست. مسیرهای یخچالی یا طناب‌محور را هم فقط وقتی کنار
  بگذارید که منبع نشان دهد این‌ها فعالیت فنیِ جدا از پیمایش پیاده‌اند، نه صرفاً
  یک Route دشوار.
- **قابل‌عبور و قابل‌توصیف:** خطرها، مواجهه، نیاز به تجهیزات یا تجربهٔ خاص و
  شرایط فصلی را از منابع بررسی و در اطلاعات Route شفاف کنید. سختی یا مخاطرهٔ
  مستند را به «مناسب مبتدی» تبدیل نکنید؛ اما صرف دشواربودن نیز Route معتبر را
  حذف نمی‌کند. شیب/geometry به‌تنهایی برای داوری کافی نیست.

لینک منبع مستقل، لینک ترک، مبدأ، landmark میانی، مقصد، شواهد شناخته‌شدن و
جمع‌بندی سختی، نوع دشواری، قابل‌عبوربودن و خطرهای مستند را در یادداشت بررسی یا
evidence catalog ثبت کنید. اگر شواهد نشان داد مسیر واقعاً صخره‌نوردی/فنی است،
پیاده نیست، یا هویت/پیوستگی/استفادهٔ واقعی آن تأیید نمی‌شود، آن را Route عمومی
نکنید. فقط اگر مقصد
کوه/قله نیست و خودرو تا خودِ نقطهٔ نماینده می‌رسد، می‌توان آن را point-only با
`routes: {}` منتشر کرد؛ در غیر این صورت انتشار مقصد هم متوقف می‌ماند تا ترک
واجدشرایط پیدا شود. `pending` جای تأیید مستقل، شناخته‌شدن، پیوستگی یا ماهیت
پیادهٔ Route را نمی‌گیرد. ترک دریافت‌شدهٔ نامناسب می‌تواند در فولدر local-only خود
باقی بماند، اما مبنای Route، distance، ascent یا ETA نیست.

این gate قاعدهٔ انتخاب/انتشار محتواست؛ به‌تنهایی تغییری در UI یا افزودن هشدار
به کاربر ایجاد نمی‌کند.

#### بررسی نقاط معنی‌دار پیش از درخواست دانلود

وجود GPX، عنوان «پیمایش بالادست» یا ثبت ارتفاع به‌تنهایی دلیل پیشنهاد یک ترک
نیست. پیش از درخواست دانلود، توضیحات، waypointها و گزارش‌های مسیر را بررسی کنید
و مبدأ، مقصد و حداقل یک نقطهٔ میانی واقعی و قابل‌شناسایی را مشخص کنید. این
نقطه می‌تواند از قبل در catalog باشد؛ لازم نیست برای هر مسیر نقطهٔ تازه بسازید.

در معرفی هر ترک، زنجیرهٔ نقاط موردنظر و دلیل نیاز به همان فایل را بنویسید.
نام‌های تأییدشده را از موارد نیازمند بررسی جدا کنید؛ waypoint بی‌نام، «محل
استراحت»، توقف کمپ یا «دشت تا ارتفاع ۲۵۰۰ متر» به‌تنهایی هویت یک مقصد یا عارضهٔ
میانی مستقل را ثابت نمی‌کند. برای ثبت دشت، نام رایج، موقعیت و هویت واقعی آن
باید با شواهد تأیید شود؛ صرف بازبودن زمین یا رسیدن ترک به یک ارتفاع کافی نیست.

اگر نقطهٔ میانی معتبر در منابع پیدا نشد، ترک را به‌عنوان مسیر آمادهٔ ثبت معرفی
نکنید و دانلود صرفاً اکتشافی/کراس‌چک نخواهید. تنها اگر دیدن GPX واقعاً برای رفع
ابهام مشخص ضروری است، همان ابهام و دلیل نیاز را پیش از درخواست دانلود توضیح
دهید؛ ثبت Route همچنان مشروط به تأیید نقاط واقعی است.

پس از دریافت ترک نیز همین کنترل تکرار شود. اگر زنجیرهٔ مبدأ → نقطهٔ میانی
معنی‌دار → مقصد تأیید نشد، Route عمومی ثبت/منتشر نشود؛ پیش‌نویس آن می‌تواند
`pending` بماند. مقصد معتبر را می‌توان مستقل با `routes: {}` منتشر کرد.
کامل‌بودن timing یا دادهٔ هواشناسی جای شواهد هویت نقاط را نمی‌گیرد.

- مسیر باید با route محصول یکی باشد: مبدأ و نقطه یکسان، جهت پیمایش روشن، مسیر
  پیوسته و قابل‌دنبال‌کردن، و یک access point واقعی داشته باشد.
- برای محصول فعلی، ترک اصلی باید مسیر پیمایش پیاده/هiking باشد و در گزارش منبع
  نیز با همین کاربری معرفی شده باشد. ترک دوچرخه، موتور، خودرو، اسب، trail پراکنده
  یا مسیر نامرتبط را برای route پیاده رد کنید. چنین ترکی اگر فقط برای تطبیق یک
  مختصات استفاده شود باید صریحاً cross-check نام‌گذاری شود و هرگز مبنای
  `distance_km`، `ascent_m` یا ETA نباشد.
- صعودی را که ماهیت واقعی آن صخره‌نوردی/سنگ‌نوردی با ابزار و حمایت فنی است، به
  عنوان hiking Route وارد نکنید. این مرز شامل شیب تند، دست‌به‌سنگِ معمول یا
  کوه‌پیمایی دشوار نیست؛ دشواری مسیر باید مستند و در معرفی آن شفاف باشد.
- مسیرهای بسیار پراکنده، بی‌نام، کم‌اعتبار یا بدون گزارش روشنِ مبدأ/نقطه را
  انتخاب نکنید. برای route اصلی ترجیحاً دو ترک مستقلِ پیاده از منابع معتبر را
  تطبیق دهید؛ اگر فقط یک ترک موجود است، فاصله و نقاط آن را با گزارش مسیر یا منبع
  مستقل کنترل کنید و confidence/uncertainty را محافظه‌کارانه ثبت کنید.
- عنوان، نوع فعالیت، توضیحات، distance، ascent و endpointهای منبع را قبل از
  استفاده بخوانید. `hiking-trails` در URL به‌تنهایی کافی نیست؛ محتوای صفحه باید
  واقعاً مسیر پیادهٔ موردنظر را تأیید کند.
- ترک باید برای route یک خط پیوسته از origin تا target بدهد. فایل round-trip یا
  نزولی فقط پس از تعیین جهت و نقطهٔ cut استفاده شود؛ timestamp خام GPX چندروزه
  زمان حرکت معتبر نیست و برای moving time/ETA استفاده نمی‌شود.
- هر route عمومی حداقل سه نقطهٔ واقعی دارد: مبدأ، حداقل یک landmark میانیِ
  نام‌دار و مستند، و نقطه. اگر route واقعاً کوتاه است، باز هم نباید نقطهٔ جعلی
  برای رسیدن به عدد سه ساخته شود؛ در آن حالت شواهد را تکمیل یا route را pending
  نگه دارید.
- فاصلهٔ نقاط یک route را با مختصات canonical کنترل کنید، نه فقط با ترتیب
  waypointهای GPX. دو نقطهٔ همان route که کمتر از ۱۰۰ متر فاصله دارند فقط وقتی
  هر دو عارضهٔ مستقل و برای کاربر مفیدند قابل انتشارند؛ اگر تفاوت واقعی یا ارزش
  forecast/مرحله‌ای ندارند، نقطهٔ جدید را اضافه نکنید و نقطهٔ تکراری را merge
  کنید. فاصلهٔ کمتر از ۲۵ متر همیشه duplicate است؛ ۲۵ تا ۱۰۰ متر نیازمند review
  مستند در `reviewed_nearby_point_pairs` است. cumulative timing نیز باید برای
  نقاط باقی‌مانده strictly increasing بماند.

### تحویل لینک ترک برای دانلود

پیش از لینک، طبق بخش «بررسی نقاط معنی‌دار پیش از درخواست دانلود» بنویسید این
ترک کدام مبدأ، نقطهٔ میانی و مقصد را پوشش می‌دهد و کدام مورد هنوز تأیید نشده
است. معرفی مبهمی مثل «پیمایش بالادست» بدون توضیح نقاط و کاربرد فایل کافی نیست.

وقتی از کاربر می‌خواهید ترک را دانلود کند، هر لینک را **به‌تنهایی در یک بلوک
کد جداگانه** و به‌صورت URL خام قرار دهید تا کنار همان لینک دکمهٔ Copy نمایش داده
شود و برای کپی نیازی به بازکردن لینک یا انتخاب متن با ماوس نباشد. عنوان و توضیح
ترک بیرون بلوک بیاید؛ داخل بلوک فقط یک URL باشد. اگر چند ترک واقعاً لازم است،
برای هرکدام همین قالب را جداگانه تکرار کنید؛ چند URL را در یک بلوک نگذارید.

تعداد لینک‌ها را به حداقل لازم برای کار محدود کنید و ترک صرفاً کراس‌چک یا تکراری
پیشنهاد ندهید، مگر آنکه برای رفع ابهام ضروری باشد. اگر ترک مناسب و قابل‌اتکایی
پیدا نشد، این را شفاف بگویید و لینک نامرتبط یا حدسی نسازید. مسیر صخره‌نوردیِ
واقعاً فنی و ابزار/طناب‌محور را به‌عنوان ترک Route پیاده جا نزنید؛ سختی زیاد،
شیب تند و دست‌به‌سنگِ معمول به‌تنهایی دلیل حذف مسیر نیست.

### قرارداد فولدر ترک

به‌محض شروع نقطه جدید، فولدر را در checkout محلی بسازید؛ اگر وجود ندارد، agent
باید خودش آن را بسازد و از کاربر بخواهد فایل‌ها را همان‌جا بگذارد:

```bash
cd /path/to/hawatch
mkdir -p tracks/<point-slug>
```

نام فایل باید بدون بازکردن فایل نیز قابل‌فهم باشد؛ الگوی پیشنهادی:
`<point>-<side-or-access>-<origin>-to-<target>-<year>.gpx`، مثلاً:
`tracks/gahar/gahar-dorud-cheshmeh-khieh-to-lake-2014.gpx`.
فایل‌های دانلودشدهٔ مبهم را قبل از تحلیل rename کنید و mapping را در
`tracks/<point-slug>/manifest.json` ثبت کنید. اگر یک فایل reverse یا فقط
cross-check است، آن را در نام و manifest مشخص کنید.

اگر کاربر فایل‌ها را در `~/Downloads` (یا پوشهٔ دانلود دیگری) گذاشت، این
فولدر فقط محل تحویل موقت است و workflow با همان نام خام ادامه پیدا نمی‌کند.
agent باید پیش از تحلیل، هر فایل را با hash/نام بررسی کند، آن را با نام
معنادار به `tracks/<point-slug>/` منتقل کند و همان نام نهایی را در manifest
ثبت کند. اگر فایل هم‌محتوا از قبل در فولدر مقصد وجود داشت، duplicate ساخته
نشود و فقط تطبیق hash گزارش شود. GPX و manifest همچنان local-only و ignored
هستند؛ چیزی از `Downloads` یا `tracks/` وارد commit، image یا سرور نمی‌شود.

### تعیین‌تکلیف همهٔ ترک‌های دانلودشده

این کار برای هر مقصد جدید اجباری است و فقط به فایلی که در پیام جاری فرستاده
شده محدود نمی‌شود. فایل‌های ترک را در `~/Downloads`، پوشه‌های Telegram مثل
`~/Downloads/Telegram Desktop` و مسیر دانلود تنظیم‌شدهٔ Telegram فهرست کنید؛
فقط قالب‌های ترک (`.gpx`, `.kml`, `.kmz`, `.fit`, `.tcx`) و آرشیوی را بررسی
کنید که نام یا محتوایش واقعاً به ترک مربوط است. فایل‌های شخصی و آرشیوهای نامرتبط
را دست نزنید.

- هش هر فایل را با همهٔ فایل‌های `tracks/**` و فایل‌های دانلودشدهٔ همان دور کار
  مقایسه کنید؛ صرفاً شباهت نام، duplicate بودن را ثابت نمی‌کند.
- فایل یکتای مرتبط را **move کنید، نه copy**؛ نام معنادار بدهید، در
  `tracks/<point-slug>/` بگذارید و در manifest با URL منبع، هش و نقش
  `primary_candidate`، `crosscheck`، `review_only` یا `rejected` ثبت کنید.
- اگر هش دقیقاً در پوشهٔ مقصد موجود است، نسخهٔ دوم نسازید و فقط دانلود تکراری را
  به Trash منتقل کنید. اگر چند دانلود یکسان است و هنوز نسخه‌ای در `tracks/`
  نیست، یکی را move کنید و باقی نسخه‌های هم‌هش را به Trash منتقل کنید. هرگز
  نسخهٔ یکتای نگه‌داری‌شده در `tracks/` را برای پاک‌سازی حذف نکنید.
- فایل نامرتبط یا ترک ردشده را با دلیل در یادداشت بررسی تعیین‌تکلیف کنید و از
  پوشهٔ دانلود پاک کنید؛ ترک `review_only` را در فولدر مقصد نگه دارید تا بررسی
  بعدی بدون تکرار دانلود ممکن باشد.
- پیش از پایان کار، فهرست Downloads/Telegram را دوباره کنترل کنید و تعداد
  فایل‌های منتقل‌شده، duplicateهای حذف‌شده و موارد باقی‌مانده با علت را گزارش
  دهید. برای ترک‌های مربوط به مقصد جاری، فایل بی‌تکلیف در پوشهٔ موقت باقی نماند.

رینیم بخشی از workflow اجباری است، نه کار اختیاری بعد از import. بعد از دانلود،
هر فایل را با نامی که نقطه، جبهه/مبدأ، نقطه مسیر و سال را نشان دهد به همان فولدر
منتقل کنید؛ سپس نام جدید را عیناً در manifest بنویسید. نمونهٔ صریح برای هزار:

```bash
cd /path/to/hawatch
mv tracks/hazar/qlh-hzr-khrmn-24-shhrywr-402-z-msyr-abshr-ryn.gpx \
  tracks/hazar/hazar-rayen-waterfall-parking-to-summit-2023-roundtrip.gpx
mv tracks/hazar/swd-bh-qlh-hzr-z-msyr-abshr-ryn.gpx \
  tracks/hazar/hazar-rayen-waterfall-parking-to-summit-2019.gpx
```

قبل از ادامه، نام‌ها و local-only بودن فولدر را کنترل کنید:

```bash
find tracks/<point-slug> -maxdepth 1 -type f -printf '%f\n' | sort
git check-ignore -v tracks/<point-slug>/*.gpx tracks/<point-slug>/manifest.json
```

اگر `git check-ignore` برای همهٔ فایل‌ها خروجی نداد، قبل از ساخت catalog باید
`.gitignore` را اصلاح کنید؛ GPX و manifest نباید هیچ‌وقت وارد commit، image یا
سرور شوند.

کل `tracks/` از ابتدا تا انتها local-only است: نه commit، نه Docker image، نه
کپی روی سرور و نه سرو از API. manifest هم فقط برای تحلیل local است و runtime آن
را نمی‌خواند. وضعیت license را تا زمان تأیید `unverified` نگه دارید.

ترتیب کار با ترک:

1. فایل‌های دانلودشده را با الگوی نام‌گذاری بالا rename کنید و نام نهایی را در
   manifest ثبت کنید.
2. منبع و نوع فعالیت هر ترک را بررسی و ترک‌های دوچرخه/خودرو، صخره‌نوردیِ فنیِ
   ابزار/طناب‌محور یا پراکنده را حذف کنید؛ شیب تند و دست‌به‌سنگِ معمول به‌تنهایی
   دلیل حذف نیست. مسیر انتخابی را با گزارش مستقل تطبیق دهید.
3. نقاط named واقعی را از waypoint و geometry استخراج کنید؛ `Waypoint`،
   `Park`، `Rest area` و «شیب نهایی» بدون landmark واقعی وارد catalog نشوند.
4. manifest را بسازید، `timestamp_quality` و `license_status` را صریح ثبت کنید.
   اگر ترک علاوه بر پیاده‌روی شامل دسترسی جاده‌ای است یا فایل از قله به مبدأ
   ضبط شده، در همان entry فیلد `route_origin` با `latitude`/`longitude` مبدأ
   واقعی پیاده و `direction` برابر `forward` یا `reverse` بگذارید. analyzer
   بخش مبدأ تا قله را جدا می‌کند و خروجی را همیشه به ترتیب مبدأ → قله می‌دهد؛
   فایل اصلی GPX را دست‌کاری یا کوتاه نکنید.
5. analyzer را فقط local و read-only اجرا کنید و خروجی آن را با منبع مسیر مقایسه
   کنید؛ analyzer خودش catalog را تغییر نمی‌دهد:

```bash
python3 scripts/analyze_route_tracks.py \
  --manifest tracks/<point-slug>/manifest.json \
  --catalog /tmp/<point-slug>_v1.json \
  > /tmp/<point-slug>_tracks_report.json
```

6. فقط پس از قبولی این gate، `distance_km`، `ascent_m`، نقاط میانی و cumulative
   timing را وارد catalog کنید. GPX `<ele>` به‌تنهایی elevation truth نیست.

### Route (اختیاری)

اگر نقطه route دارد، برای هر مسیر:

- `slug`، عنوان، subtitle، برچسب جبهه و origin/point label؛
- آرایهٔ `points` به‌ترتیب حرکت از مبدأ تا نقطه؛
- `sort_order` مثبت؛ عدد کمتر زودتر نمایش داده می‌شود؛
- `featured: true` فقط برای مسیرهای پیشنهادی UI است و ترتیب را تعیین نمی‌کند؛
- `distance_km` و `ascent_m` فقط وقتی ثبت شوند که evidence کافی دارند.

یک WeatherPoint می‌تواند بین چند Route مشترک باشد. برای آن یک slug بسازید و
همان slug را در چند مسیر استفاده کنید؛ برای هر مسیر RoutePoint جداگانه ساخته
می‌شود و timing آن مسیر را دارد.

اگر یک مسیر در کاتالوگ نقطه جدید از نقطهٔ canonical یک نقطه موجود شروع یا عبور
می‌کند، آن نقطه را دوباره در `weather_points` کپی نکنید. ابتدا کاتالوگ مالک آن
نقطه را import کنید، سپس slug آن را در آرایهٔ اختیاری
`shared_weather_points` بگذارید و همان slug را در `routes.*.points` استفاده
کنید. Loader نقطه را از دیتابیس resolve می‌کند و مالکیت، مختصات و ارتفاع آن را
تغییر نمی‌دهد. اگر slug در دیتابیس موجود نباشد یا live/active نباشد، import
fail می‌شود. نمونهٔ فعلی: route دریاچهٔ تار → زرین‌کوه از `tar-lake` مشترکِ
کاتالوگ `tar_v1.json` استفاده می‌کند؛ بنابراین کلیک روی نقطهٔ شروع به صفحهٔ
canonical `/points/tar-lake` می‌رود. رکورد قدیمیِ ساحل تار صفحهٔ مستقلی ندارد
و در لینک‌های جدید استفاده نمی‌شود.

### زمان‌بندی arrival-aware

اگر می‌خواهیم زیر هر نقطهٔ مسیر زمان رسیدن و آب‌وهوای همان زمان نمایش داده شود،
route باید timing کامل داشته باشد:

```json
{
  "timing_status": "estimated",
  "one_way_minutes": 650,
  "timing": {
    "method": "gpx-geometry+dem+web-reports-v1",
    "version": "damavand-timing-v1",
    "confidence": "medium",
    "uncertainty_minutes": 90,
    "source_urls": ["https://example.org/source"],
    "cumulative_minutes": {
      "trailhead": 0,
      "shelter": 270,
      "summit": 650
    }
  }
}
```

قواعد اجباری:

- `timing_status` باید `estimated` یا `curated` باشد؛
- `one_way_minutes` زمان صعود یک‌طرفه در سرعت متوسط است؛
- cumulative برای تمام نقاط مسیر لازم است؛
- مقدار اول صفر و همهٔ مقادیر بعدی strictly increasing باشند؛
- مقدار نهایی cumulative با `one_way_minutes` برابر باشد؛
- method، version، confidence، uncertainty و حداقل یک source URL ثبت شوند؛
- timestamp ثبت‌شدهٔ یک GPX چندروزه، زمان حرکت مسیر نیست؛ استراحت/شب‌مانی نباید
  وارد ETA شود؛
- اگر timing قابل‌دفاع نیست، route باید `pending` بماند. در این حالت forecast
  عمومی نقطه موجود است، اما arrival forecast عمداً ساخته نمی‌شود.

سرعت‌های آرام و سریع در runtime از زمان متوسط مشتق می‌شوند (`1.25` و `0.80`).
لازم نیست برای هر سرعت سه مجموعه timing جداگانه ذخیره شود.

## تنظیم نقاطی محبوب هوم

لیست بدون query در `GET /api/v1/points/` همان لیست نقاطی محبوب هوم است و
حداکثر چهار رکورد برمی‌گرداند. جست‌وجوی endpoint جداگانه همچنان نقاطی فعال
غیرمحبوب را هم پیدا می‌کند. برای تغییر لیست روی local یا سرور، slugها را به
ترتیب نمایش به command بدهید:

```bash
cd apps/api
uv run python manage.py set_popular_points \
  tochal damavand alamkuh tar-lake
```

یا با comma-separated:

```bash
docker compose --env-file .env -f infra/compose/compose.yaml exec -T api \
  python manage.py set_popular_points \
  --slugs tochal,damavand,alamkuh,tar-lake
```

این command به‌صورت اتمیک همهٔ نقاطی دیگر را از لیست محبوب خارج می‌کند، ترتیب
را از ۱ تا ۴ می‌نویسد و اگر slug ناشناخته یا بیشتر از چهار مورد داده شود هیچ
تغییری نگه نمی‌دارد. برای خالی‌کردن لیست از `--clear` استفاده کنید.

## GPX و manifest

اگر GPX دارید، آن را فقط در checkout محلی زیر `tracks/<point>/` بگذارید.
کل `tracks/` در Git ignore است و نباید commit، image یا سرور شود. `manifest.json`
فقط mapping فایل GPX به route، کیفیت timestamp و وضعیت license است؛ API در زمان
seed یا ingest آن را نمی‌خواند.

تحلیل محلی:

```bash
cd /path/to/hawatch

python3 scripts/analyze_route_tracks.py \
  --manifest tracks/damavand/manifest.json \
  --catalog /tmp/damavand_v1.json \
  > /tmp/damavand_tracks_report.json
```

خروجی distance، صعود نرم‌شده و نزدیک‌ترین نقطهٔ track را گزارش می‌کند؛ خودش
catalog را تغییر نمی‌دهد. timing نهایی تصمیم editorial است و باید با گزارش مسیر
و منابع وب/میدانی ثبت شود، نه اینکه یک timestamp خام بدون بررسی وارد ETA شود.

## جزئیات اجرای روال؛ فقط بخش‌های لازم را اجرا کنید

### ۱. ساخت و ویرایش catalog روی local

یک فایل مثل `/tmp/damavand_v1.json` بسازید. این فایل باید shape نمونهٔ
`apps/api/fixtures/catalog/tochal_v1.json` را داشته باشد و route timing کامل
داشته باشد اگر قرار است arrival weather نمایش داده شود.

قبل از ساخت JSON، برای هر کوه/قله یا مقصدی که خودرو تا خودِ آن نمی‌رسد، فولدر
`tracks/<point-slug>/` را بسازید، ترک GPX پیاده را دریافت/بررسی کنید و معیارهای
«حداقل کیفیت route و انتخاب ترک» را اجرا کنید؛ برای هر Route حداقل origin، یک
landmark میانی واقعی و target لازم است. برای point-onlyهای مجاز (مقصد غیرکوهی که
خودرو تا خودِ آن می‌رسد) فولدر و GPX لازم نیست. نبود GPX به‌خودی‌خود forecast را
برای نقطه‌ای که از قبل مجاز به point-only است متوقف نمی‌کند؛ اما برای مقصد route-
اجباری انتشار را متوقف می‌کند. بدون evidence کافی distance/ascent/ETA قطعی یا
Route عمومیِ ناقص منتشر نشود.

برای شروع می‌توان از
[`templates/catalog-template.json`](templates/catalog-template.json) یک کپی
گرفت و همهٔ مقادیر نمونه را با دادهٔ نقطه واقعی جایگزین کرد. فایل template عمداً
یک route `pending` دارد تا مسیر ناقص به‌اشتباه به‌عنوان arrival-ready منتشر نشود.

برای اجرای import لازم نیست فایل را ابتدا روی سرور کپی کنید؛ JSON می‌تواند
از فایل محلی/موقت و stdin خوانده شود. اما پیش از تحویل کار، fixture فعال را در
repository نسخه‌دار و commit/push کنید تا دیپلوی کامل آن را stale تشخیص ندهد.
runtime بعد از import همچنان دیتابیس است، نه فایل JSON.

### ۲. اعتبارسنجی محلی provider و ارتفاع

این فرمان هیچ database write ندارد و از Open-Meteo برای elevation و forecast
ساعتی استفاده می‌کند:

```bash
cd /path/to/hawatch
python3 scripts/validate_open_meteo_catalog.py \
  --catalog /tmp/damavand_v1.json
```

validator مستقل عمداً stdlib-only و بدون اتصال به DB باقی مانده است تا قبل از
نصب محیط API نیز قابل اجرا باشد؛ این مسیر، استثنای آفلاین workflow است. تمام
درخواست‌های runtime (`ingest_open_meteo` و providerهای آینده) باید فقط از
`WeatherHttpTransport` و pool فعال `WeatherProxy` استفاده کنند و مستقیماً
`urlopen` را صدا نزنند.

این مرحله gate اجباری بعد از آماده‌کردن WeatherPointها و قبل از هر `seed` است.
اگر حتی یک point خطا بگیرد، نباید catalog یا آن point وارد دیتابیس شود؛ همان
خروجی شامل slug نقطه و علت خطا باید به درخواست‌کننده/چت گزارش شود و مختصات یا
ارتفاع نباید بی‌دلیل حدس زده و silently اصلاح شود. خطاهای blocking شامل این‌هاست:

- مختصات نامعتبر، پاسخ elevation نامعتبر یا نبودن elevation منبع‌دار؛
- فاصلهٔ grid پاسخ Open-Meteo بیشتر از `۶ km`؛ این سقف فعلاً سراسری و موقت
  است؛ فاصلهٔ بیشتر از `۵ km` برای نقاط کوهستانی باید به‌عنوان کاهش دقت مکانی
  جداگانه در نظر گرفته شود؛
- نبودن `time`، دما، بارش یا `weather_code` ساعتی، یا ناهماهنگی طول آرایه‌ها؛
- اختلاف بیشتر از `۱۰۰ m` بین ارتفاع catalog و DEM، مگر اینکه مقدار catalog
  اصلاح و دوباره اعتبارسنجی شود.

validator برای هر خطای بالا exit code غیرصفر می‌دهد. `publish_catalog.py --apply`
این validator را قبل از اتصال به سرور اجرا می‌کند و در صورت خطا به مرحلهٔ
`seed_catalog` نمی‌رسد. گزینه‌های `--skip-provider-validation` و
`--allow-unresolved-elevation` فقط برای بررسی draft هستند و با `--apply` مجاز
نیستند. `seed_catalog --check-only` فقط shape JSON را می‌سنجد و جای این gate
را نمی‌گیرد.

این بررسی باید نشان دهد:

- مختصات در محدودهٔ WGS84 و تکراری نیستند؛
- همهٔ routeها فقط به pointهای موجود اشاره می‌کنند؛
- برای هر point دادهٔ ساعتی provider وجود دارد؛
- فاصلهٔ مرکز grid provider حداکثر ۶ کیلومتر است؛ سقف فعلاً سراسری و موقت است؛
  برای نقاط کوهستانی فاصلهٔ بیش از ۵ کیلومتر همچنان هشدار دقت مکانی دارد؛
- اختلاف elevation catalog و DEM حداکثر `۱۰۰ متر` است؛ بیشتر از آن failure است.

این تست ثابت نمی‌کند پیش‌بینی weather از نظر MAE در دنیای واقعی «دقیق» است؛
فقط می‌سنجد نقطه به grid درست وصل است و forecast قابل دریافت است. سنجش دقت
تجربی نیازمند observation واقعی/ایستگاه مرجع و workflow جداگانه است.

### ۳. یک اجرای wrapper برای check و publish

برای افزودن معمولی، `publish_catalog.py --apply` را یک‌بار اجرا کنید؛ خود wrapper
به‌ترتیب gate محلی Open-Meteo/DEM، check شکل JSON روی سرور، import اتمیک، ingest
هدفمند و preflight نقطه را اجرا می‌کند. اجرای جداگانهٔ check-only و سپس apply،
اعتبارسنجی شبکه‌ای را تکرار می‌کند و لازم نیست. حالت بدون `--apply` فقط وقتی
مناسب است که عمداً می‌خواهید قبل از انتشار check-only بگیرید و اجرای بعدیِ apply
و تکرار gate برایتان قابل قبول است.

```bash
python3 scripts/publish_catalog.py \
  --catalog apps/api/fixtures/catalog/<catalog>_v1.json \
  --host hawatch \
  --point <primary-point-slug> \
  --apply
```

در حالت apply، wrapper به‌ترتیب زیر عمل می‌کند:

1. دوباره از pass شدن gate محلی Open-Meteo/DEM مطمئن می‌شود؛
2. catalog را با `seed_catalog --stdin --strict` به‌صورت اتمیک import می‌کند؛
3. فقط slugهای همین catalog را با `ingest_open_meteo` می‌گیرد؛
4. `catalog_preflight --point ... --require-forecast --strict` را اجرا می‌کند؛
5. اگر همه‌چیز pass شود، نقطه آمادهٔ refresh صفحه است.

### ترتیب انتشار و بررسی URL عمومی (برای جلوگیری از cache شدن 404)

هرگز URL canonical نقطه یا مسیر جدید را قبل از رسیدن fixture به سرور و sync شدن
دیتابیس از طریق دامنهٔ عمومی بررسی نکنید. اگر origin هنوز آن slug را نمی‌شناسد،
CDN ممکن است همان پاسخ `404` موقت را cache کند و بعد از اصلاح origin نیز آن را
تحویل دهد. این اتفاق به معنی خرابی catalog یا نیاز به تغییر کد CDN نیست.

برای افزودن افزایشی، fixture نسخه‌دار را در Git نگه دارید و یک‌بار از local با
`publish_catalog.py --apply` import کنید؛ فایل از stdin ارسال می‌شود و لازم نیست
برای این کار کل checkout سرور pull یا `sync_catalog` شود. این تغییر به restart یا
recreate سرویس نیاز ندارد. `sync_catalog` را فقط برای همگام‌سازی عمدی کل مجموعهٔ
fixtureها یا cleanup گسترده به‌کار ببرید. پس از publish، پاسخ origin/API را
read-only کنترل کنید و سپس URL canonical عمومی را باز کنید:

```bash
ssh hawatch 'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api \
  python manage.py catalog_preflight --point <primary-point-slug> --require-forecast'

ssh hawatch 'curl -fsS -o /dev/null -w "%{http_code}\\n" \
  -H "Host: hawatch.ir" http://127.0.0.1/points/<point-slug>'
```

`publish_catalog.py --apply` خودش ingest و preflight را انجام می‌دهد؛ فرمان
`catalog_preflight` بالا فقط برای بررسی دستیِ بعدی است و لازم نیست دوباره اجرا
شود.

اگر origin `200` است اما دامنهٔ عمومی هنوز `404` می‌دهد، ابتدا همان URL canonical
و در صورت نیاز URL مسیر را در CDN purge کنید؛ از purge گسترده استفاده نکنید.
برای تشخیص read-only می‌توان یک query موقت هم زد، اما query به‌دلیل سیاست SEO
ممکن است `noindex,follow` باشد و نباید جایگزین بررسی canonical شود.

### پیگیری ایندکس URLهای جدید

پس از انتشار عمومی موفق، URL canonical هر Point یا Route فعال را در
[`indexing-backlog.md`](indexing-backlog.md) ثبت کنید، به شرطی که Point دارای
`seo_indexable: true` باشد یا Route فعال و قابل ایندکس باشد. URL یک مقصد جدید و
هر Route تازه‌ای که در همان کار اضافه شده، جداگانه ثبت می‌شوند؛ اگر برای Point
موجود Route جدیدی اضافه شد، URL همان Route را هم وارد صف کنید. waypointهای
`seo_indexable: false`، queryدار، redirect، 404 و Route غیرفعال وارد صف نمی‌شوند.

این بک‌لاگ اختلاف با آخرین گزارش Google را نگه می‌دارد، نه وضعیت زندهٔ ایندکس.
وقتی کاربر URL مشخصی را ایندکس‌شده اعلام کرد، همان URL را از صف جاری حذف کنید؛
صرف درخواست ایندکس یا پاسخ 200 برای حذف کافی نیست. وقتی کاربر چند URL بعدی را
برای درخواست می‌خواهد، به‌ترتیب P0 تا P3 از بک‌لاگ انتخاب کنید و در صورت وجود،
آن‌ها را با گزارش تازهٔ Search Console/URL Inspection تطبیق دهید. پیش از درخواست،
canonical، robots و status عمومی URL را نیز کنترل کنید.

اگر عمداً route بدون timing اضافه می‌کنید، باید آگاهانه استفاده کنید:

```bash
python3 scripts/publish_catalog.py \
  --catalog /tmp/draft.json \
  --host root@SERVER_IP \
  --apply \
  --allow-pending-timing
```

این گزینه مشکل را پنهان نمی‌کند؛ route در دیتابیس `pending` می‌ماند و arrival
weather آن در UI نمایش داده نمی‌شود. برای launch عمومی بهتر است بدون این گزینه
کار کنید تا missing timing جلوی publish گرفته شود.

### ۴. معادل دستی روی سرور

این مسیر فقط وقتی wrapper در دسترس نیست. پیش از هر import باید
`validate_open_meteo_catalog.py` با `pass=True` تمام شده باشد؛
`seed_catalog --check-only` به‌تنهایی اعتبار weather یا ارتفاع را بررسی نمی‌کند.
خطای provider را با slug نقطه گزارش کنید و import را انجام ندهید. این fallback
از اجرای wrapper طولانی‌تر است و برای روال عادی پیشنهاد نمی‌شود.

اگر wrapper در دسترس نبود، از root checkout سرور:

```bash
ssh root@SERVER_IP \
  'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api python manage.py seed_catalog --stdin --check-only' \
  < /tmp/damavand_v1.json

ssh root@SERVER_IP \
  'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api python manage.py seed_catalog --stdin --strict' \
  < /tmp/damavand_v1.json

ssh root@SERVER_IP \
  'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api python manage.py ingest_open_meteo --slugs <comma-separated-weather-point-slugs-from-this-catalog>'

ssh root@SERVER_IP \
  'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api python manage.py catalog_preflight --point damavand --require-forecast --strict'
```

در فرمان‌های بالا `/tmp/damavand_v1.json` روی local خوانده می‌شود و از stdin
عبور می‌کند؛ لازم نیست `/tmp` روی سرور وجود داشته باشد.

برای بررسی نقطه بدون تغییر:

```bash
ssh root@SERVER_IP \
  'cd /root/hawatch && docker compose --env-file .env -f infra/compose/compose.yaml exec -T api python manage.py catalog_preflight --point damavand --require-forecast'
```

در `catalog_preflight`، حالت `--strict` warningهای timing را هم failure می‌کند.
برای نقطه‌ای که هنوز timing ندارد، `pass=False` با warning طبیعی است؛ این نشانهٔ
خرابی ingest نیست.

### وضعیت فعلی دماوند

برای دماوند، چهار route اصلی با timing تخمینی اولیه وارد دیتابیس شده‌اند:

| route | زمان متوسط یک‌طرفه | عدم‌قطعیت | وضعیت |
| --- | ---: | ---: | --- |
| جنوبی | ۶۱۵ دقیقه | ±۹۰ دقیقه | estimated |
| غربی | ۶۹۰ دقیقه | ±۹۰ دقیقه | estimated |
| شمال‌شرقی | ۶۵۰ دقیقه | ±۹۰ دقیقه | estimated |
| شمالی | ۷۵۰ دقیقه | ±۹۰ دقیقه | estimated |

این اعداد برای اتصال forecast به زمان رسیدن استفاده می‌شوند و field-curated
نیستند؛ بعداً با چند track مستقل و گزارش میدانی می‌توان آن‌ها را به‌روزرسانی کرد.
GPX شمالی timestamp معتبر برای محاسبهٔ moving time نداشت و timestamp خام آن در
این timing استفاده نشده است.

### کاتالوگ‌های بازگردانده‌شده

چهار Point اصلی زیر اکنون fixture مستقل و canonical خود را دارند؛ هیچ‌کدام
Destination نیستند و تمام URLها از الگوی `/points/{slug}` پیروی می‌کنند:

| Point | Routeهای fixture |
| --- | --- |
| علم‌کوه (`alamkuh`) | جنوبی حصارچال، شمالی سیاه‌سنگ |
| دماوند (`damavand`) | جنوبی، غربی، شمال‌شرقی، شمالی |
| دشت دریاسر (`daryasar`) | اِسِل‌محله تا دشت دریاسر |
| آبشار اسکلیم (`eskelim`) | پارکینگ تا آبشار اسکلیم |

هر نقطهٔ میانی در این چهار fixture نام مکان‌دار و slug یکتا دارد؛ نقطهٔ دید
یا برچسب عمومی برای پرکردن timeline اضافه نشده است. ارتفاع‌های provisional
با Open-Meteo GLO-90 DEM اعتبارسنجی شده‌اند و برای دقت میدانی بالاتر در آینده
باید با منبع محلی مستقل بازبینی شوند.

### ۵. مسیر Admin بدون JSON

برای ورود دستی:

1. Admin → WeatherPoint: slug، نام، مختصات، elevation، `is_active=true` و
   `ingest_enabled=true`؛ `fixture_managed` را دستی true نکنید.
2. فیلدهای metadata و `seo_indexable` را روی همان WeatherPoint canonical تکمیل
   کنید؛ برای waypoint فنی false و برای مقصد مستقل/عارضهٔ شاخص true است.
3. Admin → Route: نقطه فعال، عنوان، `sort_order` و active.
4. RoutePointها را به‌ترتیب بسازید و برای همه `cumulative_minutes` وارد کنید.
5. بعد از save، publish service ترتیب، origin/target، segment، axis و timing را
   normalize می‌کند؛ timing ناقص عمداً pending می‌شود.
6. ingest هدفمند را اجرا و preflight را چک کنید.

برای اضافه‌کردن سریع نقاطی متعدد، JSON + wrapper پیشنهاد می‌شود؛ Admin برای
اصلاح یک رکورد یا override اپراتوری مناسب‌تر است.

### Definition of Done برای نقطه جدید

نقطه فقط وقتی «آمادهٔ نمایش» محسوب می‌شود که همهٔ این موارد برقرار باشند:

1. category/icon از کلیدهای موجود انتخاب شده و نقطه ناخواسته وارد popular home
   نشده باشد.
2. canonical point WeatherPoint و همهٔ route pointها مختصات WGS84، ارتفاع
   منبع‌دار و نام قابل‌شناسایی، زمینه‌دار و قابل جست‌وجوی مستقل داشته باشند؛
   نام مبهم یا عمومی به‌تنهایی کافی نیست. ارتفاع provisional باید همین‌طور
   برچسب بخورد و GPX `<ele>` جای آن را نگیرد.
3. اگر `routes` خالی نیست، هر route حداقل origin → landmark واقعی → target،
   ترتیب `sort_order` و timing کامل یا وضعیت آگاهانهٔ `pending` داشته باشد.
4. اگر route وجود دارد، همهٔ ترک‌های مورد استفاده، hiking مناسب و پیوسته باشند؛
   هیچ ترک دوچرخه، خودرو، صخره‌نوردیِ فنیِ ابزار/طناب‌محور، پراکنده یا نامرتبط
   در محاسبهٔ route وارد نشده باشد. سختی یا دست‌به‌سنگِ معمول به‌تنهایی دلیل رد نیست.
5. برای هر مقصد، بررسی مسیر در وب انجام و نتیجه ثبت شده باشد. هر کوه/قله و هر
   مقصدی که خودرو تا خودِ آن نمی‌رسد، باید Route پیاده با GPX بررسی‌شده داشته
   باشد؛ ترک و دست‌کم یک منبع مستقل خارج از Wikiloc همان مسیر را تأیید کنند و
   شواهد شناخته‌شدن، پیوستگی و قابل‌عبوربودن را نشان دهند؛ دشواری مسیر به‌تنهایی
   مانع نیست و باید مستند و شفاف نمایش داده شود. مسیر صخره‌نوردیِ فنی Route پیاده
   محسوب نمی‌شود. اگر این gate پاس نشد، مقصد منتشر نشود. point-only فقط برای مقصد
   غیرکوهیِ قابل‌دسترسی با خودروی عادی تا خودِ نقطهٔ نماینده مجاز است.
6. validator محلی، check-only remote، import strict، ingest و preflight strict
   pass شده باشند؛ validator باید برای هر point پاسخ elevation، grid نزدیک و
   دادهٔ ساعتی کامل گزارش کند و برای هر point forecast ذخیره‌شده وجود داشته باشد.
7. صفحهٔ نقطه و تمام routeها با API واقعی refresh و از نظر نام، مختصات، timing و
   weather point بررسی شده باشند.
8. `tracks/` و manifest local-only، ignored و خارج از commit باقی مانده باشند.
9. پس از تأیید URL عمومی، تمام Point/Routeهای فعال و indexable از این انتشار در
   [`indexing-backlog.md`](indexing-backlog.md) ثبت شده باشند؛ URLهای `noindex`
   و Routeهای غیرفعال اضافه نشده باشند.

## حل خطاهای رایج

### `timed_routes=0` یا `زمان‌بندی در دسترس نیست`

نقاط forecast دارند اما route timing ندارد یا cumulative یکی از نقاط خالی است.
دوباره ingest کردن این مشکل را حل نمی‌کند. timing را به JSON اضافه و دوباره با
`seed_catalog --stdin --strict` import کنید.

### `provider_checked=17` ولی route هنوز خالی است

این حالت طبیعی است: provider برای WeatherPointها موفق بوده، اما API برای اتصال
forecast به نقطهٔ مسیر به arrival time نیاز دارد. timing و `cumulative_minutes`
را بررسی کنید.

### `Catalog input is valid; No database changes made`

این خروجی `--check-only` است و موفقیت آن به معنی import نیست. مرحلهٔ apply را
بعد از بررسی اجرا کنید.

### slug conflict

import معمولی non-destructive است. ردیف operator-managed overwrite نمی‌شود؛ در
حالت strict کل import rollback می‌شود. slug موجود را reuse کنید یا conflict را
در Admin بررسی کنید؛ `--force-adopt` فقط با تصمیم صریح اپراتور استفاده شود.

### دادهٔ هوا قدیمی است

ingest scheduler طبق timezone تهران در ساعت‌های ۰۰:۰۰، ۰۶:۰۰، ۱۲:۰۰ و ۱۸:۰۰
اجرا می‌شود. برای refresh فوری:

```bash
docker compose --env-file .env -f infra/compose/compose.yaml run --rm ingest
```

سپس preflight را اجرا کنید. frontend مستقیماً به Open-Meteo وصل نمی‌شود؛ فقط
forecast ذخیره‌شدهٔ دیتابیس را می‌خواند.

## چک‌لیست قبل از اعلام آماده‌بودن

- [ ] نام و slug با بررسی هم‌نام‌ها در کل catalog، دیتابیس و منابع بیرونی انتخاب
      شده‌اند؛ کوتاه‌ترین هویت معنادار و یکتا هستند و دلیل هر پسوند ثبت شده است.
- [ ] نقطه و canonical point WeatherPoint مختصات و elevation منبع‌دار دارند.
- [ ] برای مقصد جدید، routeهای پیاده در وب بررسی و نتیجه ثبت شده است. هر کوه/قله
      و مقصدی که خودرو تا خودِ آن نمی‌رسد، پیش از انتشار Route پیادهٔ دارای GPX
      بررسی‌شده می‌خواهد؛ همان مسیر باید علاوه بر ترک در دست‌کم یک منبع مستقل
      خارج از Wikiloc تأیید شده و مسیر پیادهٔ واقعی، پیوسته و قابل‌عبور باشد؛
      سختی، شیب تند یا دست‌به‌سنگِ معمول مانع پذیرش نیست و باید شفاف توصیف شود.
      مسیر صخره‌نوردیِ فنی Route پیاده محسوب نمی‌شود. اگر این شرط‌ها برقرار
      نیستند، مقصد منتشر نشده است. point-only فقط برای مقصد
      غیرکوهیِ قابل‌دسترسی با خودروی عادی تا خودِ نقطهٔ نماینده مجاز است.
- [ ] اگر نقطه route دارد، هر route `sort_order` درست و points مرتب از مبدأ تا نقطه دارد.
- [ ] هر Route عمومی حداقل یک نقطهٔ میانی واقعی و مستند، غیر از مبدأ و مقصد،
      دارد؛ توقف کمپ، waypoint بی‌نام یا برچسب ارتفاعی جای آن را نگرفته است.
- [ ] اگر route دارد، distance/ascent عمومی قابل‌دفاع و timingهای arrival دارای provenance هستند.
