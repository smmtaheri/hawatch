# قرارداد واحد افزودن نقطه و مسیر

این سند مسیر مرجع برای هر نقطه جدید است. کاتالوگ JSON ورودی قابل بازتولید است؛
دیتابیس منبع حقیقت runtime است. redirect قدیمی نداریم: slug جدید canonical است
و URL قبلی عمداً ممکن است 404 شود. SEO عمومی P0 با gate `seo_indexable` و
sitemap نقطه/مسیر در همین قرارداد فعال است.

## مالکیت catalog و افزودن نقطهٔ جدید

قبل از نوشتن JSON مشخص کنید نقطهٔ جدید مالک کدام catalog است. هر slug نقطه و هر
slug مسیر باید در کل پوشهٔ `apps/api/fixtures/catalog/` فقط یک مالک داشته باشد:

- نقطهٔ مستقل را دقیقاً یک‌بار در `weather_points` فایل مالک تعریف کنید؛ اگر در
  مسیر catalog دیگری استفاده می‌شود، آن را دوباره تعریف نکنید و فقط در
  `shared_weather_points` و `routes.*.points` با همان slug ارجاع دهید.
- اگر نقطهٔ جدید به یک catalog موجود اضافه می‌شود، همان فایل فعال را ویرایش کنید
  و `catalog_version` را به نسخهٔ بعدی تغییر دهید. فایل نسخهٔ قبلی را کنار فایل
  جدید در پوشهٔ fixture نگه ندارید؛ loader عمداً مالکیت تکراری را خطا می‌کند.
  تاریخچهٔ نسخهٔ قبلی در Git باقی می‌ماند.
- `routes: {}` فقط برای مقصد غیرکوهی مجاز است که خودِ نقطهٔ نماینده‌اش با
  خودروی عادی و از راه غیرآفرودی قابل‌دسترسی باشد. هر کوه/قله و هر مقصدی که
  خودرو تا خودِ آن نمی‌رسد، پیش از انتشار صفحه باید Route پیادهٔ واجد شرایط و
  ترک GPX بررسی‌شده داشته باشد؛ اگر ترک معتبر نداریم، مقصد را point-only منتشر
  نکنید و انتشار را متوقف کنید. برای point-only مجاز، فقط canonical WeatherPoint
  را اضافه کنید و `routes: {}` بگذارید.
- اگر نقطه مسیر دارد، هر Route باید زنجیرهٔ واقعی مبدأ → landmark مستند → نقطه
  داشته باشد. route جاده‌ای/خودرویی یا صخره‌نوردیِ فنیِ ابزار/طناب‌محور را
  hiking route ثبت نکنید؛ مسیر دشوار پیاده و دست‌به‌سنگِ معمول مجاز است.
- بررسی route برای هر مقصد جدید بخشی از onboarding است، حتی اگر تصمیم نهایی
  point-only باشد. Route عمومی فقط وقتی پذیرفته است که خودِ همان مسیر علاوه بر
  ترک، دست‌کم در یک منبع مستقل وب خارج از Wikiloc توصیف/تأیید شده باشد، مسیر
  شناخته‌شده و واقعاً پیاده، پیوسته و قابل‌عبور باشد. سختی/خیلی‌سختی، شیب تند
  یا دست‌به‌سنگِ معمول به‌تنهایی دلیل رد نیست و باید شفاف توصیف شود. مسیر
  صخره‌نوردی/سنگ‌نوردیِ فنی (ابزار/طناب‌محور) hiking Route محسوب نمی‌شود. مسیر
  اصلی و جاافتاده را مقدم کنید و مسیر فرعی را فقط وقتی کنار بگذارید که مسیر اصلی
  بهتر و مستندتری وجود دارد. محبوبیت Wikiloc به‌تنهایی کافی نیست؛ اگر شواهد
  مستقل، پیوستگی یا قابل‌عبوربودن احراز نشد، ترک را منتشر نکنید؛ مقصد فقط در صورتی
  point-only می‌ماند که کوه/قله نباشد و خودرو تا خودِ نقطهٔ نماینده برسد. در
  غیر این صورت انتشار مقصد نیز متوقف می‌شود. جزئیات غربالگری در
  [راهنمای onboarding](catalog-onboarding.md) آمده است.
- نقاط یک Route را از نظر فاصلهٔ مختصات canonical، مخصوصاً نقاط متوالی، بررسی
  کنید. نقطه‌ای که کمتر از ۱۰۰ متر با نقطهٔ همان مسیر فاصله دارد باید landmark
  مستقل، نام روشن و ارزش واقعی برای کاربر (اطلاعات/هوا یا مرحلهٔ متفاوت) داشته
  باشد؛ صرفاً waypoint نزدیک یا تقسیم مصنوعی مسیر کافی نیست. فاصلهٔ کمتر از ۲۵
  متر duplicate محسوب می‌شود و باید merge شود؛ بازهٔ ۲۵ تا ۱۰۰ متر فقط با
  بررسی و ثبت علت روشن در `reviewed_nearby_point_pairs` مجاز است.
- slug باید lowercase، hyphenated، بدون underscore و پایدار باشد؛ `page_name`
  نیز در تمام catalogها یکتا و زمینه‌دار باشد. `seo_indexable` فقط قابلیت
  ایندکس‌شدن را کنترل می‌کند، نه فعال‌بودن یا نمایش نقطه: نقاط فنی و بین‌راهی
  مثل پارکینگ، چشمهٔ مسیر، گردنه، یال و مبدأ فنی را صریحاً `false` کنید. این
  نقاط همچنان در مسیر، جست‌وجو، API و forecast می‌مانند، اما صفحهٔ مستقلشان
  `noindex,follow` است و در sitemap نمی‌آید. برای عارضهٔ مستقلِ قابل جست‌وجو
  `true` بگذارید؛ اگر یک نوع فنی بدون این فیلد اضافه شود، policy مرکزی آن را
  به‌طور پیش‌فرض noindex می‌کند. نقطهٔ جدید خودکار محبوب Home نمی‌شود.

### کوتاه‌ترین هویت معنادار و یکتا

این بررسی پیش از ساخت هر WeatherPoint، انتخاب فولدر ترک و نوشتن catalog اجباری
است؛ فقط به آزادبودن slug در fixture فعلی یا نوع «قله» اکتفا نکنید.

1. نام فارسی، شکل‌های املایی/نام‌های رایج و آوانویسی انگلیسی را در کل catalogها
   و WeatherPointهای دیتابیس، از جمله نقاط پشتیبان و noindex، بررسی کنید. اگر
   همان مکان از قبل ثبت شده است، رکورد canonical آن را reuse کنید.
2. در منابع بیرونی جست‌وجو کنید آیا همان نام برای قله، روستا، شهر، محله، دره،
   جنگل، دریاچه یا مقصد طبیعت‌گردی دیگری هم استفاده می‌شود؛ بررسی فقط نقاط
   موجودِ هواچ کافی نیست. مختصات، نوع عارضه و منطقهٔ موارد هم‌نام را تطبیق دهید.
   پیدا نکردن نتیجه در جست‌وجو اثبات قطعی نبودن هم‌نام نیست؛ اگر ابهام مؤثر باقی
   ماند، قبل از انتشار آن را گزارش و با منبع معتبر رفع کنید.
3. کوتاه‌ترین نام رایج و قابل‌جست‌وجوی مستقل و کوتاه‌ترین slug معنادار و یکتا
   را انتخاب کنید؛ نام را مخفف، ساختگی یا صرفاً برای کوتاهی نامفهوم نکنید.
   در نام فارسی نوع واقعی مثل «قلهٔ آهنگرک» یا «روستای آهار» می‌تواند برای
   فهم کاربر لازم باشد، ولی لازم نیست همهٔ این کلمات در slug تکرار شوند.
4. اگر بررسی نام، هویت مستقل و بدون ابهام را تأیید کرد، شکل ساده مانند
   `ahangarak` یا `esterchal` مناسب است؛ `-peak` یا `-village` را خودکار اضافه
   نکنید. اگر هم‌نام واقعی وجود دارد، فقط کمترین qualifier لازم را اضافه کنید:
   نوع عارضه برای تمایز قله/روستا، یا منطقه برای دو عارضهٔ هم‌نوع. گردنهٔ مستقل
   استرچال با `esterchal-pass` تفکیک می‌شود. پیشوند نام قلهٔ مادر یا خط‌الرأس
   صرفاً به‌علت قرارگرفتن یک مقصد در مسیر آن مجاز نیست؛ باید بخشی از هویت واقعی
   یا برای رفع ابهام ضروری باشد.
5. نتیجهٔ بررسی و منابع را در evidence هویت (`source_urls` و توضیح لازم در
   `identity_summary` یا یادداشت پژوهش) ثبت کنید؛ برای هر qualifier دلیل روشن
   داشته باشید. پیش از انتشار، نام در مقصدها، عنوان تب/SEO، H1، توضیح زیر هدر،
   search و RoutePointهای مرتبط و تمام ارجاع‌های canonical را کنترل کنید؛
   قالب «آب‌وهوای ...» یا کوتاه‌سازی آگاهانهٔ برچسب مسیر نباید هویت متناقض بسازد.

این قاعده مجوز تغییر خودکار URLهای منتشرشده نیست. اصلاح نام/slug موجود باید
در یک تغییر مجزای درخواست‌شده، با به‌روزرسانی تمام مصرف‌کننده‌ها و طبق سیاست
URL همان تغییر انجام شود؛ برای احتمال صرفِ اضافه‌شدن مقصدی در آینده URL سالم
را طولانی یا عوض نکنید.

### عضویت خودکار مقصدهای مستقل در Hub

اگر نقطه یک مقصد مستقل و معروف برای جست‌وجوی کاربر است (برای نمونه قله، دریاچه،
آبشار، دشت، جنگل یا روستای شناخته‌شده)، آن را در همان catalog با
`kind: "primary"`، `importance: "primary"` و `seo_indexable: true` ثبت کنید.
Hub داده‌محور `/destinations` همین رکوردها را خودکار پیدا می‌کند؛ بنابراین برای
هر مقصد جدید URL یا لیست دستی در frontend نسازید. Route پیادهٔ کامل و مستند برای
مقصدهای پیمایشی لازم است. هر کوه/قله و مقصدی که خودرو تا خودِ آن نمی‌رسد باید
پیش از انتشار Route پیادهٔ واجد شرایط با ترک GPX بررسی‌شده داشته باشد؛ نبود ترک
معتبر مانع انتشار همان مقصد می‌شود و نباید آن را با point-only دور زد. `routes:
{}` فقط برای مقصد غیرکوهیِ قابل‌دسترسی با خودروی عادی تا خودِ نقطهٔ نماینده مجاز
است. وضعیت pending فقط برای Route ناقص یا فاقد شواهد است، نه برای صفحهٔ مقصد.
waypointهای فنی و نقاط
صرفاً بین‌راهی با `seo_indexable: false` همچنان در route/API/search می‌مانند اما
وارد Hub و sitemap نمی‌شوند. قبل از import duplicate مختصات/نام را در کل
catalog و دیتابیس بررسی کنید و نوع واقعی عارضه را ثبت کنید.

برای افزودن عادی و افزایشی، catalog نسخه‌دار را با
`validate_catalog --file <catalog> --strict` بررسی و یک‌بار با
`scripts/publish_catalog.py --apply` منتشر کنید. wrapper خودش gate اجباری
Open-Meteo/DEM، check شکل remote، import اتمیک، ingest هدفمند و preflight نقطه را
اجرا می‌کند؛ اجرای check-only جداگانه و بعد apply، provider را بی‌دلیل دوباره
صدا می‌زند. `publish_catalog.py` فایل را از stdin می‌فرستد و fixture را در
repository جایگزین نمی‌کند؛ fixture نسخه‌دار باید در Git باقی بماند.

برای این import افزایشی backup، migration، restart یا `sync_catalog` لازم نیست.
بدون `--prune`، seed اتمیک است و ردیف‌های operator-managed را حذف یا overwrite
نمی‌کند. `sync_catalog --dry-run/--apply` را فقط برای همگام‌سازی عمدی مجموعهٔ
کامل fixtureها یا cleanup گسترده اجرا کنید؛ backup هم برای عملیات تخریبی/گسترده
یا migration پرریسک است، نه برای هر نقطهٔ جدید. انتخاب محبوب Home با syncهای
بعدی حفظ می‌شود.

### دروازهٔ سراسری duplicate قبل از هر افزودن

این کنترل برای همهٔ نقاط جدید و همهٔ catalogهاست، نه فقط برای catalog یا Route
در حال ویرایش. قبل از ثبت هر نقطه، مختصات candidate را با تمام
WeatherPointهای فعال در کل `apps/api/fixtures/catalog/` و دیتابیس مقایسه کنید.
اگر نقطهٔ موجود همان عارضه است، slug و رکورد موجود را دوباره استفاده کنید و
تعریف جدید نسازید. فاصلهٔ کمتر از ۲۵ متر duplicate قطعی است؛ فاصلهٔ ۲۵ تا ۱۰۰
متر فقط برای دو عارضهٔ واقعی و نام‌دار، با ثبت slugها و دلیل در
`reviewed_nearby_point_pairs`، پذیرفته می‌شود. نام متفاوت یا قرارگرفتن نقطه در
Route دیگر به‌تنهایی مجوز ساخت duplicate نیست. برای هر افزودن، نام/alias را در
fixtureها جست‌وجو و یک lookup مکانی فقط‌خواندنی روی دیتابیس برای نزدیک‌ترین
WeatherPointهای فعال انجام دهید؛ query نمونه در
[`catalog-onboarding.md`](catalog-onboarding.md#روال-سریع-پیش‌فرض-برای-افزودن-نقطه)
است. `validate_catalog --all --database --strict` مقایسهٔ زوج‌به‌زوج کل دیتابیس
را انجام می‌دهد و برای افزودن معمولی لازم نیست؛ آن را برای audit کامل یا تغییرات
گسترده نگه دارید. در صورت ابهام، فقط همان نقطه را تا بررسی منابع و مختصات دقیق
متوقف کنید.

HTML اولیهٔ SEO از دیتابیس runtime ساخته می‌شود. مقصدهای مستقل برای Hub
`/destinations` باید در Catalog با `kind: "primary"`، `importance: "primary"`
و `seo_indexable: true` ثبت شوند؛ Hub آن‌ها را خودکار پیدا می‌کند و فهرست
hardcode ندارد. بنابراین Point یا Route جدید
پس از import/sync، بدون افزودن URL hardcode، prerender جداگانه یا build frontend
در `/points/<slug>` یا `/routes/<slug>` هم title، canonical و محتوای اولیهٔ
اختصاصی می‌گیرد. تنها تغییر کد renderer به deploy معمول imageهای API و web نیاز
دارد؛ جزئیات در [`seo.md`](seo.md) است.

برای تغییرات گستردهٔ Catalog یا audit دوره‌ای، گراف کامل لینک‌های قابل‌خزش را
بررسی کنید:

```bash
python manage.py validate_catalog --all --database --check-links --strict
```

این validator باید برای هر مقصد ورودی Hub، برای هر Route ورودی از مقصد، و برای
هر Point indexable غیرمقصد ورودی از مقصد یا Route واقعی پیدا کند. شهر، روستا یا
محلهٔ indexableِ بدون Route باید در همان catalog نسخه‌دار کنار مقصد اصلیِ مرتبط
ثبت شده باشد تا renderer لینک واقعی از مقصد به نقطهٔ دسترسی و از نقطهٔ دسترسی به
مقصد بسازد؛
این رابطه برای catalogهای آینده هم بدون فهرست slug دستی کار می‌کند. اگر Point
مستقلِ بدون مسیر دارید، آن را مقصد اصلی کنید؛ برای waypoint فنی
`seo_indexable: false` بگذارید تا صفحه‌اش فقط `noindex,follow` باشد.

## ۱. اطلاعات لازم

برای هر نقطه:

- `point.slug` یکتا، نام فارسی، `category_key`، منطقه، مختصات WGS84،
  ارتفاع و منبع ارتفاع، `climate`، تصویر و alt؛
- ارتفاع نسبت به مبنای سطح دریای جهانی می‌تواند منفی باشد (مانند ساحل خزر)؛
  مقدار معتبر DEM را صفر یا مثبت‌سازی نکنید.
- همان WeatherPoint با همان مختصات/ارتفاع؛ نقطهٔ شاخص `kind: "primary"` و سایر
  نقاط `kind: "shared"` یا `kind: "route_point"` می‌گیرند. همین رکورد تنها
  هویت عمومی نقطه و منبع forecast است و به `/points/{slug}` می‌رود؛
- اگر مقصد کوه/قله است یا خودرو تا خودِ مقصد نمی‌رسد، Route پیاده و ترک GPX
  بررسی‌شده پیش‌نیاز انتشار صفحه است؛ در نبود ترک واجد شرایط، WeatherPoint را
  برای انتشار live نسازید. `routes: {}` فقط برای مقصد غیرکوهی مجاز است که خودِ
  نقطهٔ نماینده‌اش با خودروی عادی قابل‌دسترسی باشد. مسیر آفرودی، خودرو، دوچرخه
  یا صخره‌نوردیِ فنیِ ابزار/طناب‌محور را hiking route ثبت نکنید؛ دشواری و
  دست‌به‌سنگِ معمول به‌تنهایی دلیل رد نیست.

برای هر WeatherPoint مستقل:

- slug انگلیسی lowercase با hyphen، بدون underscore، `name` و `short_label`؛
- `page_name` یکتا و قابل جست‌وجوی مستقل، `place_type`، `identity_summary`؛
- نام نقطه باید زمینه‌دار و از نظر جست‌وجو مستقل باشد. نام‌هایی مثل «تپهٔ
  گوگردی» یا «استراحتگاه» به‌تنهایی قابل انتشار نیستند؛ آن‌ها را به شکل
  «تپهٔ گوگردی دماوند» یا «استراحتگاه مسیر شمالی علم‌کوه» بنویسید تا با نقاط
  مشابه قاطی نشوند. اگر چنین نام یکتایی برای عارضه وجود ندارد، نقطه را اضافه
  نکنید و صرفاً برای بهترشدن SEO نام ساختگی نسازید.
- `importance` یکی از `primary`/`support` و `name_status` یکی از
  `official`/`established`/`descriptive`؛
- `climate` باید یکی از profileهای demo (`alpine`، `desert`، `forest_fog`، `high_alpine`، `lake_valley` یا `meadow`) باشد؛ validator و Admin مقدار ناشناخته را قبل از import/save رد می‌کنند؛
- `seo_indexable` را برای discoverability تعیین کنید: مقدار `false` برای
  waypointهای صرفاً فنی مجاز است و آن رکورد نباید از `is_active` یا زنجیرهٔ
  Route خارج شود. نقطهٔ noindex همچنان صفحهٔ ۲۰۰، API، جست‌وجو و forecast دارد؛
  فقط meta/X-Robots آن `noindex,follow` و sitemap از آن خالی است؛ فهرست داخلی
  برای حفظ مسیر و جست‌وجو آن را نگه می‌دارد.
  نبود flag برای place typeهای فنی طبق policy مرکزی noindex می‌شود؛ برای
  استثناهای مهم مثل ایستگاه تله‌کابین یا پناهگاه معروف، `true` را صریح بنویسید؛
- `aliases` برای شکل‌های رایج جست‌وجو و `source_urls` برای منابع هویت/موقعیت؛
- مختصات دقیق و `elevation_m` معتبر به‌همراه `elevation_source` یا evidence.
- بلوک اختیاری `seo` فقط وقتی اضافه شود که copy آن کوتاه، منبع‌دار و واقعاً
  مفید است. کلیدهای مجاز `title`، `description` و `content` هستند؛ نبود بلوک
  قالب عمومی پویا را فعال می‌کند. متن حدسی، keyword-stuffed یا تکراری را وارد
  catalog نکنید.

`page_name` نباید عبارت عمومی مثل «استراحتگاه مسیر» یا «شیب نهایی قله» باشد.
نام باید عارضهٔ واقعی را با زمینهٔ نقطه مشخص کند؛ برای مثال «جان‌پناه امیری
توچال» یا «روستای کلاک بالا». نقطهٔ شاخص در slug خود
باید بدون underscore باشد؛ همهٔ نقاط، از جمله نقاط شاخص، صفحهٔ canonical خود را
در `/points/{slug}` دارند.

## ۲. ترک و نقاط مسیر

در شروع کار agent باید این فولدر را در checkout محلی بسازد:

```bash
cd /path/to/hawatch
mkdir -p tracks/<point-slug>
```

هر ترک باید مسیر پیادهٔ شناخته‌شده و پیوسته‌ای با مبدأ و نقطه مشخص باشد. ترک
دوچرخه، خودرو، موتور، مسیر واقعی صخره‌نوردی/سنگ‌نوردیِ ابزار/طناب‌محور، ترک
پراکنده یا مسیر نامرتبط برای hiking Route قابل قبول نیست. شیب تند، دست‌به‌سنگِ
معمول یا برچسب دشوار به‌تنهایی دلیل رد نیست. اگر یک ترک نزولی است، فقط پس از تعیین جهت و تطبیق
با منبع مستقل می‌توان آن را برعکس تحلیل کرد؛ timestamp و ارتفاع خام GPX به‌تنهایی
حقیقت نیستند.

علاوه بر صفحهٔ ترک، برای همان مسیر دست‌کم یک منبع وب مستقل خارج از Wikiloc لازم
است؛ منبع باید خود مسیر و مبدأ/جهت آن را شرح دهد، نه فقط مقصد را معرفی کند.
Route عمومی باید مسیر پیادهٔ واقعی، شناخته‌شده و قابل‌عبور باشد. مسیر اصلی صعود
را در اولویت بگذارید؛ سختی/خیلی‌سختی، شیب تند یا دست‌به‌سنگِ معمول دلیل رد نیست
و باید با جزئیات مستند شود. مسیر صخره‌نوردی/سنگ‌نوردیِ فنی را hiking Route ثبت
نکنید؛ منظور مسیر فنی ابزار/طناب‌محور است، نه scrambling یا کوه‌پیمایی دشوار.
مسیر فرعی فقط وقتی کنار گذاشته شود که مسیر اصلیِ بهتر و مستندتری موجود باشد.
برای هر مقصد این جست‌وجو انجام می‌شود؛ اگر مسیر پیادهٔ معتبر پیدا نشد، مقصد کوه
یا پیاده‌دسترس را با `routes: {}` منتشر نکنید.

پیش از درخواست دانلود، مبدأ، مقصد و حداقل یک نقطهٔ میانی معنی‌دار را از
منابع مشخص و همراه معرفی ترک بیان کنید؛ نقاط موجود را reuse کنید. وجود GPX یا
عنوان «پیمایش بالادست» کافی نیست. اگر هویت نقطه‌ای مبهم است، ابهام را صریح
بگویید و فقط وقتی بررسی فایل برای رفع همان ابهام ضروری است دانلود بخواهید،
نه برای جست‌وجوی احتمالی یک نقطه. پس از تحلیل نیز بدون تأیید این زنجیره Route
عمومی منتشر نشود؛ مقصد فقط در صورت واجد شرایط بودن برای point-only می‌تواند بدون
Route بماند، وگرنه انتشارش متوقف است. معیار و قالب معرفی در
[بررسی نقاط معنی‌دار پیش از درخواست دانلود](catalog-onboarding.md)
آمده است.

برای Route اجباریِ کوه/قله یا مقصد پیاده‌دسترس، ترک GPX محلی و بررسی‌شده لازم
است؛ برای route اصلی ترجیحاً دو ترک مستقل تطبیق داده شود. هر route عمومی باید حداقل
زنجیرهٔ `مبدأ → یک عارضهٔ واقعی میانی → نقطه` داشته باشد. نقطهٔ ساختگی یا generic
برای پرکردن این زنجیره اضافه نشود؛ اگر landmark میانی اثبات نشده، route pending
بماند.

مبدأ نزدیک روستا باید با نقطهٔ canonical همان روستا ادغام شود، نه اینکه برای
مسجد، پارکینگ یا waypoint شروعِ داخل بافت روستا صفحهٔ دوم ساخته شود. تنها
access point مستقل و واقعاً دور از روستا با نام مستند می‌تواند نقطهٔ جدا باشد؛
جزئیات بررسی فاصله و `reviewed_nearby_point_pairs` در بخش «ادغام مبدأهای نزدیک
روستا» راهنمای onboarding آمده است.

نام فایل دانلودی را قبل از تحلیل روشن کنید:
`<point>-<side>-<origin>-to-<target>-<year>.gpx`.
فایل‌ها و `manifest.json` در `.gitignore` هستند و هرگز commit، image یا server
نمی‌شوند. manifest فقط mapping فایل، route، منبع و نقش `primary`/`crosscheck`
را نگه می‌دارد. در هر onboarding، فایل‌های ترک Downloads و پوشه‌های دانلود
Telegram را نیز فهرست و با hash بررسی کنید: فایل یکتا را rename و move کنید،
فایل هم‌هشِ موجود در `tracks/` را دوباره نسازید و نسخهٔ دانلودیِ تکراری را به
Trash منتقل کنید. برای جزئیات تعیین تکلیف همهٔ فایل‌ها و ثبت موارد بررسی/ردشده،
از [راهنمای onboarding](catalog-onboarding.md#تعیین‌تکلیف-همهٔ-ترک‌های-دانلودشده)
پیروی کنید.

هنگام درخواست دانلود از کاربر، لینک هر ترک را جداگانه به‌صورت URL خام در بلوک
کد مستقل ارائه کنید تا دکمهٔ Copy کنار همان لینک قابل استفاده باشد؛ داخل هر
بلوک فقط یک لینک قرار دهید و عنوان/توضیح را بیرون آن بنویسید. تعداد ترک‌ها را
به موارد واقعاً لازم محدود کنید. جزئیات قالب تحویل در
[`catalog-onboarding.md`](catalog-onboarding.md#تحویل-لینک-ترک-برای-دانلود)
آمده است.

## ۳. ساخت و اعتبارسنجی محلی

از ریشهٔ repository:

```bash
python3 scripts/analyze_route_tracks.py \
  --manifest tracks/<point-slug>/manifest.json \
  --catalog /tmp/<point-slug>_v1.json

python3 scripts/validate_open_meteo_catalog.py \
  --catalog /tmp/<point-slug>_v1.json
```

فقط برای point-only مجاز مرحلهٔ تحلیل GPX را حذف کنید. اگر از `publish_catalog.py --apply`
استفاده می‌کنید، Open-Meteo/DEM gate در همان اجرا انجام می‌شود؛ validator مستقل
را جداگانه فقط برای عیب‌یابی یا پیش‌بررسی اجرا کنید تا درخواست provider تکرار
نشود.

دستور دوم برای تک‌تک pointها Open-Meteo را read-only صدا می‌زند و وجود elevation،
grid معتبر، hourly data و فاصلهٔ grid تا مختصات را بررسی می‌کند. اختلاف catalog و
DEM بیشتر از ۱۰۰ متر، grid دورتر از ۶ کیلومتر، پاسخ ناقص یا خطای هر point یعنی
کل import متوقف می‌شود؛ مختصات/ارتفاع آن point باید اصلاح یا از catalog حذف شود.
این سقف فعلاً سراسری و موقت است؛ برای نقاط کوهستانی، فاصلهٔ بیش از ۵ کیلومتر
هشدار کاهش دقت مکانی دارد.
GPX برای forecast لازم نیست، ولی برای distance/ascent/ETA و یافتن landmark لازم
است.

این validator مستقل برای اجرای پیش از نصب محیط API همچنان بدون DB و stdlib-only
است. درخواست‌های runtime و providerهای آینده باید از `WeatherHttpTransport` و
pool فعال `WeatherProxy` عبور کنند؛ credential را در fixture، migration یا
manifest قرار ندهید.

سپس قرارداد هویت و route را بررسی کنید:

```bash
cd apps/api
uv run python manage.py validate_catalog --file catalog/<file>.json
```

فرمان file-level، slug/metadata، page name و aliasهای همان catalog، route
references و sort order را بررسی می‌کند. فاصلهٔ candidate با نقاط زنده را با
lookup مکانی هدفمندِ بخش duplicate بالا بسنجید؛ لازم نیست برای هر نقطه، تمام
جفت‌های دیتابیس را دوباره محاسبه کنید. بررسی کامل fixtureها و دیتابیس هزینهٔ
بیشتری دارد و برای هر نقطه لازم نیست؛ آن را فقط پس از تغییرات گسترده یا در audit
دوره‌ای اجرا کنید:

```bash
uv run python manage.py validate_catalog --all --database --strict
```

## ۴. واردکردن روی local

برای تغییر fixture-only، `migrate` لازم نیست. به‌جای اجرای دستی چند فرمان و
ingest تمام نقاط، روال عادی همان `publish_catalog.py --apply` در بخش بعد است؛ این
wrapper فقط WeatherPointهای همان catalog را ingest می‌کند. فرمان‌های زیر برای
محیط local/تشخیص موردی‌اند:

```bash
cd apps/api
uv run python manage.py migrate
uv run python manage.py seed_catalog --file catalog/<file>.json --strict
uv run python manage.py ingest_open_meteo --slugs <point-1>,<point-2>
uv run python manage.py catalog_preflight --point <point-slug> --require-forecast --strict
```

`seed_catalog` اتمیک و idempotent است. `--prune` فقط وقتی استفاده شود که حذف
رکوردهای fixture-managed عمداً بررسی شده باشد. پس از ingest، preflight باید برای
همهٔ pointهای نقطه `provider_checked` و forecast قابل استفاده نشان دهد. پیش‌بینی
از DB خوانده می‌شود؛ frontend مستقیماً Open-Meteo را صدا نمی‌زند.

## ۵. import به سرور از روی local

فایل را روی سرور کپی نکنید؛ از stdin بفرستید. حالت استاندارد شامل validation
محلی، check راه دور، import، ingest هدفمند و preflight است:

```bash
cd /path/to/hawatch
python3 scripts/publish_catalog.py \
  --catalog /tmp/<point-slug>_v1.json \
  --host hawatch \
  --point <point-slug> \
  --apply
```

`hawatch` همان alias SSH است. اگر route عمداً timing ندارد، انتشار فقط با تصمیم
صریح و `--allow-pending-timing` مجاز است؛ در این حالت forecast نقطه‌ها می‌آید
ولی arrival weather مسیر ساخته نمی‌شود. بدون `--apply` همین دستور فقط check می‌کند
و هیچ writeای ندارد.

پس از import، برای تغییر نقاطی محبوب فقط از command ادمین استفاده کنید؛ نقطه
جدید خودکار روی Home نمی‌رود:

```bash
uv run python manage.py set_popular_points --slugs a,b,c,d
```

حداکثر چهار نقطه محبوب است. همهٔ نقاطی فعال در search قابل پیدا شدن‌اند، اما
صفحهٔ Home فقط همین چهار مورد را نشان می‌دهد.

## ۶. کنترل‌های اجباری بعد از تغییر

اگر کد Python تغییر کرده باشد، قبل از commit این بررسی‌های repository را اجرا
کنید:

```bash
cd /path/to/hawatch
git diff --check
PYTHONPATH=apps/api/src python3 -m compileall -q apps/api/src
cd apps/api && uv run python manage.py makemigrations --check
uv run pytest
```

برای تغییر fixture-only، حداقل `validate_catalog --file ... --strict` و gate
Open-Meteo را اجرا کنید (gate دوم در `publish_catalog.py --apply` انجام می‌شود)؛
full test suite، compileall و makemigrations check لازم نیستند. برای تغییر
نام/slug موجود با `git grep` مطمئن شوید slug قدیمی در catalog، API، frontend و
docs فعلی نمانده است. migrationهای تاریخی تنها سابقهٔ بازپخش schema هستند و نباید
برای compatibility URL جدید استفاده شوند. SEO عمومی P0 همین حالا روی `page_name`
و slug canonical اعمال می‌شود: نقاط فعالِ indexable و routeهای فعال وارد sitemap
می‌شوند؛ waypointهای فعالِ فنی نیز قابل بازشدن‌اند اما `noindex,follow` هستند و
از sitemap بیرون می‌مانند. queryهای برنامه‌ریزی نیز `noindex,follow` هستند.

فقط وقتی عمداً کل fixtureهای package‌شده را با دیتابیس موجود همگام می‌کنید، از
`sync_catalog` استفاده کنید. این عملیات ممکن است stale fixture-managed rows را
پاک/غیرفعال کند؛ پیش از cleanup یا sync گسترده، در صورت نیاز عملیاتی backup
بگیرید. این مرحله بخشی از افزودن افزایشی هر نقطه نیست:

```bash
docker compose --env-file .env -f infra/compose/compose.yaml exec -T api \
  python manage.py sync_catalog --dry-run
```

گزارش، created/updated/unchanged، فهرست دقیق RoutePointها و رکوردهای
fixture-managed قابل حذف یا غیرفعال‌سازی و conflictهای operator-managed را نشان
می‌دهد. پس از بازبینی همان برنامه را اتمیک اعمال کنید:

```bash
docker compose --env-file .env -f infra/compose/compose.yaml exec -T api \
  python manage.py sync_catalog --apply
```

این command فقط ردیف‌های `fixture_managed=true` را برای stale cleanup هدف می‌گیرد؛
رکوردهای دستی حفظ می‌شوند و conflict مبهم باعث توقف sync می‌شود. اجرای دوبارهٔ
`--apply` روی دادهٔ همگام‌شده باید همهٔ رکوردهای موجود را unchanged گزارش کند.
